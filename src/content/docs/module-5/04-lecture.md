## 1. Пропси: передача і отримання

**Пропси** (props, від properties — властивості) — це вхідні дані компонента. Батьківський компонент передає їх як атрибути в JSX, а React збирає всі атрибути в один об'єкт і передає його **першим аргументом** функції компонента.

```jsx
// Батьківський компонент передає пропси
<CourseCard title="React для початківців" lessons={24} level="beginner" />
```

```jsx
// Дочірній компонент отримує об'єкт props
function CourseCard(props) {
  return (
    <article className="course-card">
      <h3>{props.title}</h3>
      <p>{props.lessons} уроків · рівень: {props.level}</p>
    </article>
  );
}
```

На практиці майже завжди використовують **деструктуризацію** (destructuring) прямо в параметрах — так одразу видно, які пропси приймає компонент:

```jsx
function CourseCard({ title, lessons, level }) {
  return (
    <article className="course-card">
      <h3>{title}</h3>
      <p>{lessons} уроків · рівень: {level}</p>
    </article>
  );
}
```

Аналогія: компонент — це функція, пропси — її аргументи, а JSX-тег — виклик функції. `<CourseCard title="..." />` за змістом еквівалентно `CourseCard({ title: '...' })` (хоча викликає функцію сам React, а не ви).

### Що відбувається під капотом

```jsx
<CourseCard title="React" lessons={24} />
```

транспілюється в

```js
jsx(CourseCard, { title: 'React', lessons: 24 })
```

React зберігає цей об'єкт в елементі, а коли настає час рендеру — викликає `CourseCard({ title: 'React', lessons: 24 })`.

## 2. Типи значень пропсів. Значення за замовчуванням. Spread

### Передати можна будь-що

```jsx
<CourseCard
  title="React для початківців"         // рядок
  lessons={24}                           // число
  isFree={false}                         // логічне значення
  tags={['frontend', 'javascript']}      // масив
  author={{ name: 'Ірина', avatar: '/a.jpg' }} // об'єкт
  onEnroll={handleEnroll}                // функція
  badge={<span className="new">Новий</span>}   // JSX
/>
```

Зверніть увагу на подвійні фігурні дужки в `author={{ ... }}` — зовнішні означають «вираз», внутрішні — літерал об'єкта (так само, як у `style`).

Логічний проп без значення дорівнює `true`:

```jsx
<CourseCard title="..." featured />   // featured === true
```

### Значення за замовчуванням

Значення за замовчуванням задаються стандартним синтаксисом JavaScript при деструктуризації:

```jsx
function Avatar({ src, alt = '', size = 48, rounded = true }) {
  return (
    <img
      src={src}
      alt={alt}
      width={size}
      height={size}
      className={rounded ? 'avatar avatar--round' : 'avatar'}
    />
  );
}

<Avatar src="/me.jpg" />             // size = 48, rounded = true
<Avatar src="/me.jpg" size={96} />    // size = 96
```

:::caution[Значення за замовчуванням і null]
Значення за замовчуванням спрацьовує лише тоді, коли проп **не передано** або дорівнює `undefined`. Якщо передати `size={null}`, буде `null`, а не 48.
:::

У старому коді можна зустріти властивість `Avatar.defaultProps = { size: 48 }`. У React 19 для функціональних компонентів `defaultProps` **більше не підтримується** — використовуйте лише значення за замовчуванням у деструктуризації.

### Оператор spread `{...props}`

Якщо компонент — тонка обгортка над HTML-елементом, решту пропсів зручно «прокинути» далі:

```jsx
function TextInput({ label, id, ...inputProps }) {
  return (
    <div className="field">
      <label htmlFor={id}>{label}</label>
      <input id={id} className="field__input" {...inputProps} />
    </div>
  );
}

<TextInput id="email" label="Email" type="email" placeholder="you@mail.com" required />
```

Тут `label` і `id` використовуються явно, а `type`, `placeholder`, `required` потрапляють у `inputProps` і передаються в `<input>`.

Spread зручний і для передачі об'єкта цілком: `<CourseCard {...course} />` еквівалентно `<CourseCard id={course.id} title={course.title} ... />`. Але зловживати цим не варто: стає неочевидно, які саме пропси отримує компонент.

### Порядок має значення

Пізніші атрибути перекривають ранні:

```jsx
<button type="button" {...props}>        {/* props.type перекриє "button" */}
<button {...props} type="button">        {/* завжди "button" */}
```

## 3. Односпрямований потік даних. Пропси лише для читання

### Дані течуть згори вниз

У React дані передаються **від батька до дітей** і ніколи навпаки. Компонент `CourseCard` не знає, звідки прийшли його пропси — з масиву, з сервера чи зі стану батька. Він просто відображає те, що отримав.

```text
CoursesPage  (дані: courses)
   │  course={...}
   ▼
CourseCard
   │  name={course.author.name}  src={course.author.avatar}
   ▼
Avatar
```

Така модель робить застосунок **передбачуваним**: щоб зрозуміти, чому компонент показує певне значення, достатньо піднятися деревом угору до місця, де ці дані з'явилися.

### Пропси — тільки для читання

Компонент **ніколи не змінює** власні пропси:

```jsx
// ❌ НЕПРАВИЛЬНО: мутація пропсів
function CourseCard({ course }) {
  course.title = course.title.toUpperCase(); // змінює об'єкт батька!
  return <h3>{course.title}</h3>;
}

// ✅ ПРАВИЛЬНО: обчислюємо нове значення
function CourseCard({ course }) {
  const upperTitle = course.title.toUpperCase();
  return <h3>{upperTitle}</h3>;
}
```

Чому це важливо:

1. **Чистота.** Мутація пропсів — побічний ефект: компонент змінює дані, якими володіє хтось інший. Інші компоненти, що використовують той самий об'єкт, несподівано отримають змінені дані.
2. **React не дізнається про зміну.** Мутація не запускає повторного рендеру, тому інтерфейс розсинхронізується з даними.
3. **Оптимізації ламаються.** React і React Compiler порівнюють значення за посиланням; змінений «на місці» об'єкт виглядає незмінним.

Те саме стосується масивів: `items.sort()`, `items.push()`, `items.reverse()` змінюють вихідний масив. Використовуйте методи, що повертають новий масив: `toSorted()`, `toReversed()`, `[...items, newItem]`, `filter`, `map`.

### А якщо дані мають змінюватися?

Пропси — як аргументи функції: їх задає той, хто викликає. Якщо значення має змінюватися з часом у відповідь на дії користувача, потрібен **стан** (state). Стан компонента може стати пропсом його дітей:

| | Пропси (props) | Стан (state) |
|---|---|---|
| Звідки беруться | Передає батьківський компонент | Створює і зберігає сам компонент (`useState`) |
| Хто може змінювати | Лише власник (батько) | Лише сам компонент, через функцію-сеттер |
| Аналогія | Аргументи функції | Локальні змінні, що «пам'ятаються» між викликами |
| Зміна запускає рендер | Так (коли батько передав нові) | Так |

Стан детально розглянемо на практичній роботі 5.

## 4. Функції як пропси: події «знизу вгору»

Якщо дані течуть лише вниз, як дочірній компонент може «повідомити» батька, що користувач натиснув кнопку? Відповідь: батько передає дитині **функцію**, а дитина її викликає. Такі функції називають **колбеками** (callbacks), а пропси — за домовленістю з префіксом `on`: `onClick`, `onEnroll`, `onClose`.

```jsx
function CourseCard({ course, onEnroll }) {
  return (
    <article className="course-card">
      <h3>{course.title}</h3>
      <button onClick={() => onEnroll(course.id)}>Записатися</button>
    </article>
  );
}

function CoursesPage({ courses }) {
  // Обробник живе в батьківському компоненті
  function handleEnroll(courseId) {
    alert(`Ви записалися на курс #${courseId}`);
  }

  return (
    <div className="grid">
      {courses.map(course => (
        <CourseCard key={course.id} course={course} onEnroll={handleEnroll} />
      ))}
    </div>
  );
}
```

```text
CoursesPage ──course, onEnroll──► CourseCard     (дані і функція — вниз)
CoursesPage ◄──onEnroll(id)────── CourseCard     (виклик функції — сигнал угору)
```

Домовленості щодо назв:

| Що | Назва | Приклад |
|---|---|---|
| Проп-колбек (у дочірньому компоненті) | `on` + Подія | `onEnroll`, `onDelete`, `onChange` |
| Функція-обробник (у батьківському) | `handle` + Подія | `handleEnroll`, `handleDelete` |

### Передача функції, а не її виклику

```jsx
<button onClick={onEnroll}>             {/* ✅ передаємо функцію, але отримаємо об'єкт події */}
<button onClick={() => onEnroll(id)}>    {/* ✅ передаємо стрілкову функцію з аргументом */}
<button onClick={onEnroll(id)}>          {/* ❌ ВИКЛИК під час рендеру! */}
```

Третій варіант викличе `onEnroll` одразу при рендері кожної картки, а в `onClick` потрапить результат виклику (`undefined`). Якщо обробник змінює стан, це ще й призведе до нескінченного циклу рендерів.

### Власні компоненти і події DOM

Події на кшталт `onClick` мають особливе значення лише для **вбудованих** елементів (`<button>`, `<input>`). Для власного компонента `onClick` — це звичайний проп, який нічого не робить, доки ви не передасте його DOM-елементу:

```jsx
function Button({ children, onClick, variant = 'primary' }) {
  return (
    <button type="button" className={`btn btn--${variant}`} onClick={onClick}>
      {children}
    </button>
  );
}
```

## 5. Проп `children` і компоненти-обгортки

### Що таке children

Усе, що розміщено **між відкривальним і закривальним тегами** компонента, React передає в спеціальний проп `children`:

```jsx
<Card>
  <h3>Заголовок</h3>
  <p>Будь-який вміст</p>
</Card>
```

```jsx
function Card({ children }) {
  return <div className="card">{children}</div>;
}
```

`children` може бути рядком, одним елементом, масивом елементів або взагалі відсутнім (`undefined`). Компоненту `Card` неважливо, що всередині, — він відповідає лише за «рамку»: тінь, заокруглення, відступи. Такий підхід називають **вкладенням** (containment).

### Приклад: модальне вікно

```jsx title="Modal.jsx"
import './Modal.css';

export default function Modal({ title, isOpen, onClose, children }) {
  if (!isOpen) return null;

  return (
    <div className="modal-backdrop" onClick={onClose}>
      {/* stopPropagation: клік усередині вікна не закриває його */}
      <div className="modal" role="dialog" aria-modal="true" aria-labelledby="modal-title"
           onClick={e => e.stopPropagation()}>
        <header className="modal__header">
          <h2 id="modal-title">{title}</h2>
          <button className="modal__close" aria-label="Закрити" onClick={onClose}>✕</button>
        </header>
        <div className="modal__body">{children}</div>
      </div>
    </div>
  );
}
```

Тепер одне й те саме модальне вікно можна наповнювати будь-чим:

```jsx
<Modal title="Запис на курс" isOpen={isOpen} onClose={close}>
  <p>Ви записуєтеся на курс «{course.title}».</p>
  <Button onClick={confirm}>Підтвердити</Button>
</Modal>

<Modal title="Правила платформи" isOpen={rulesOpen} onClose={closeRules}>
  <ol>
    <li>Будьте ввічливі.</li>
    <li>Виконуйте домашні завдання вчасно.</li>
  </ol>
</Modal>
```

### Приклад: макет сторінки

```jsx title="Layout.jsx"
export default function Layout({ children }) {
  return (
    <>
      <SiteHeader />
      <main className="container">{children}</main>
      <SiteFooter />
    </>
  );
}
```

```jsx
<Layout>
  <h1>Мої курси</h1>
  <CourseList courses={myCourses} />
</Layout>
```

### Кілька «слотів»: іменовані пропси з JSX

`children` — лише один «отвір» для вмісту. Якщо компоненту потрібно кілька областей, передайте JSX через звичайні пропси. Цей патерн називають **слотами** (slots):

```jsx
function PageSection({ title, actions, footer, children }) {
  return (
    <section className="section">
      <div className="section__head">
        <h2>{title}</h2>
        {actions && <div className="section__actions">{actions}</div>}
      </div>
      <div className="section__content">{children}</div>
      {footer && <div className="section__footer">{footer}</div>}
    </section>
  );
}

<PageSection
  title="Популярні курси"
  actions={<Button variant="link">Усі курси →</Button>}
  footer={<small>Оновлено сьогодні</small>}
>
  <CourseList courses={popular} />
</PageSection>
```

## 6. Композиція замість наслідування. Патерни

### Чому не наслідування

В об'єктно-орієнтованому програмуванні спільну поведінку часто виносять у базовий клас: `class PrimaryButton extends Button`. Команда React прямо рекомендує **не будувати ієрархій наслідування компонентів**: за роки використання React у тисячах компонентів Meta не знайшла випадків, де наслідування було б кращим за композицію.

**Композиція** (composition) — побудова складних компонентів з простіших шляхом вкладення та передачі пропсів.

### Спеціалізація

«Особливий випадок» загального компонента створюється не через `extends`, а через рендер загального компонента з фіксованими пропсами:

```jsx
function Button({ variant = 'primary', size = 'md', children, ...rest }) {
  return (
    <button className={`btn btn--${variant} btn--${size}`} {...rest}>
      {children}
    </button>
  );
}

// Спеціалізації
function DangerButton(props) {
  return <Button variant="danger" {...props} />;
}

function EnrollButton({ onClick }) {
  return <Button size="lg" onClick={onClick}>Записатися на курс</Button>;
}
```

### Порівняння підходів

| Задача | Наслідування (ООП) | Композиція (React) |
|---|---|---|
| Спільний вигляд-«рамка» | Базовий клас із шаблонним методом | Компонент-обгортка з `children` |
| Особливий випадок | `class Danger extends Button` | `<Button variant="danger" />` |
| Кілька змінних областей | Абстрактні методи | Слоти — пропси з JSX |
| Спільна логіка (не вигляд) | Базовий клас | Власні хуки (практична 13) |
| Спільні дані на багатьох рівнях | Статичні поля, синглтони | Контекст (практична 13) |

### Патерн «контейнер — презентаційний компонент»

Корисно розділяти компоненти на два види:

- **презентаційні** (presentational) — лише відображають отримані пропси: `CourseCard`, `Avatar`, `Button`. Їх легко повторно використовувати і тестувати;
- **контейнерні** (container) — знають, звідки брати дані, зберігають стан, містять обробники: `CoursesPage`, `App`.

```jsx
// Контейнер: дані + логіка
function CoursesPage() {
  const courses = useCourses();          // звідкись отримує дані
  const handleEnroll = id => { /* ... */ };
  return <CourseGrid courses={courses} onEnroll={handleEnroll} />;
}

// Презентаційний: лише відображення
function CourseGrid({ courses, onEnroll }) {
  return (
    <div className="grid">
      {courses.map(c => <CourseCard key={c.id} course={c} onEnroll={onEnroll} />)}
    </div>
  );
}
```

Це не жорстке правило, а орієнтир: «розумних» компонентів має бути небагато, «простих» — більшість.

### Компоненти як значення

Оскільки компонент — це функція, його можна передати пропсом або обрати динамічно:

```jsx
const icons = { video: VideoIcon, text: TextIcon, quiz: QuizIcon };

function LessonItem({ lesson }) {
  const Icon = icons[lesson.type];   // змінна з великої літери!
  return (
    <li>
      <Icon size={16} /> {lesson.title}
    </li>
  );
}
```

## 7. Prop drilling

Уявіть, що ім'я поточного користувача зберігається в `App`, а потрібне воно в `UserMenu`, глибоко в шапці:

```text
App (user)
└── Layout          user={user}   ← сам не використовує, лише передає
    └── SiteHeader  user={user}   ← сам не використовує, лише передає
        └── Nav     user={user}   ← сам не використовує, лише передає
            └── UserMenu user={user}   ← нарешті використовує
```

Передача пропсів через проміжні компоненти, яким вони не потрібні, називається **prop drilling** («просвердлювання» пропсів). Проблеми:

- проміжні компоненти «знають» про дані, які їх не стосуються;
- при додаванні нового пропса доводиться змінювати весь ланцюжок;
- важче повторно використовувати проміжні компоненти.

Два-три рівні передачі — нормально і навіть добре (потік даних явний). Коли ланцюжок довшає, є два рішення:

1. **Композиція через `children`.** Часто проміжні компоненти можна не «прокидати», а **передати їм готовий елемент**:

   ```jsx
   // Замість <Layout user={user} />:
   <Layout header={<SiteHeader menu={<UserMenu user={user} />} />}>
     ...
   </Layout>
   ```

   Тепер `Layout` і `SiteHeader` взагалі не знають про `user`.

2. **Контекст** (Context API) — механізм, що дозволяє будь-якому вкладеному компоненту отримати значення без передачі через проміжні рівні. Розглянемо на практичній 13, коли кошик магазину стане потрібен на кількох сторінках.

:::tip
Перш ніж тягнутися до контексту, спробуйте композицію. Офіційна документація React радить саме такий порядок.
:::

## 8. Перевірка пропсів і документування

JavaScript не перевіряє типи, тому легко передати `lessons="24"` (рядок) замість `lessons={24}` або забути обов'язковий проп.

| Інструмент | Статус | Коментар |
|---|---|---|
| `PropTypes` (пакет `prop-types`) | **Застарів.** У React 19 перевірки `propTypes` видалено — React їх ігнорує | Трапляється у старих проєктах |
| **TypeScript** | Галузевий стандарт | Перевірка типів пропсів під час написання коду і збирання |
| JSDoc-коментарі | Легка альтернатива | VS Code показує підказки при використанні компонента |

У курсі ми пишемо на JavaScript, тому для складних компонентів корисно додавати JSDoc:

```jsx
/**
 * Картка курсу.
 * @param {{ course: { id: number, title: string, lessons: number }, onEnroll: (id: number) => void }} props
 */
export default function CourseCard({ course, onEnroll }) { /* ... */ }
```

## 9. Як розбити інтерфейс на компоненти

Документація React пропонує підхід «Thinking in React». Для статичної частини (без стану) він виглядає так:

1. **Обведіть на макеті кожну логічну частину** і дайте їй назву. Принцип єдиної відповідальності: один компонент — одна задача. Якщо компонент розростається — розбийте його.
2. **Побудуйте ієрархію.** Компонент, що лежить усередині іншого на макеті, — його дочірній компонент.
3. **Зробіть статичну версію**: компоненти лише з пропсами, без стану. Дані передавайте згори.
4. Далі (на наступних заняттях): визначте мінімальний **стан**, вирішіть, **де він живе**, і додайте зворотний потік даних через колбеки.

Приклад для сторінки курсів:

```text
CoursesPage
├── PageSection (title="Популярні курси", actions=...)
│   └── CourseGrid
│       └── CourseCard × N
│           ├── Avatar
│           ├── Rating
│           └── Button
└── Modal (title="Запис на курс")
    └── EnrollForm
```

### Коли виносити компонент

| Ознака | Приклад |
|---|---|
| Фрагмент повторюється | Картка, рядок таблиці, кнопка певного стилю |
| Фрагмент має чітку власну відповідальність | Рейтинг зірочками, бейдж статусу |
| Компонент перевищує ~100–150 рядків | Сторінка з кількома секціями |
| Фрагмент має власний стан | Розкривний блок, вкладки |

І навпаки: не варто виносити в компонент кожен `<span>` — надмірне дроблення так само шкодить читабельності.

## Підсумки

- **Пропси** — вхідні дані компонента; React передає їх одним об'єктом, який зручно деструктуризувати. Передати можна будь-яке значення: рядок, число, об'єкт, функцію, JSX.
- Значення за замовчуванням задаються в деструктуризації; `defaultProps` і `propTypes` у React 19 для функцій не працюють.
- Дані течуть **згори вниз**; пропси **лише для читання** — компонент ніколи їх не змінює.
- Щоб дитина повідомила батька про подію, батько передає **функцію-колбек** (`onSomething`).
- **`children`** — вміст між тегами компонента; основа компонентів-обгорток. Для кількох областей використовують слоти — пропси з JSX.
- React рекомендує **композицію замість наслідування**: спеціалізація через фіксовані пропси, вкладення через `children`.
- **Prop drilling** — передача пропсів через рівні, яким вони не потрібні. Рішення — композиція або контекст.
