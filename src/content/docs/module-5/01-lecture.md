## 1. Від сторінок до застосунків: проблема імперативного DOM

У попередніх модулях ви писали інтерфейси на «чистому» JavaScript (vanilla JS): знаходили елементи через `document.querySelector`, змінювали `textContent`, додавали класи, створювали вузли через `createElement` і вішали обробники `addEventListener`. Для невеликої сторінки це цілком нормальний підхід. Проблеми починаються, коли інтерфейс росте.

### Імперативний підхід

**Імперативний** (imperative) код описує, **як** змінити інтерфейс — покроково: «знайди елемент», «зміни текст», «додай клас», «видали вузол». Розгляньмо простий список завдань із лічильником невиконаних:

```js title="todo.js (vanilla JS)"
const list = document.querySelector('#list');
const counter = document.querySelector('#counter');
const input = document.querySelector('#new-task');
let tasks = [];

function addTask(text) {
  const task = { id: Date.now(), text, done: false };
  tasks.push(task);

  // 1. Створюємо DOM-вузол для нового завдання
  const li = document.createElement('li');
  li.dataset.id = task.id;
  li.innerHTML = `<label><input type="checkbox"> ${text}</label>`;
  li.querySelector('input').addEventListener('change', () => toggleTask(task.id, li));
  list.append(li);

  // 2. Не забуваємо оновити лічильник
  updateCounter();
}

function toggleTask(id, li) {
  const task = tasks.find(t => t.id === id);
  task.done = !task.done;
  li.classList.toggle('done', task.done); // 3. Синхронізуємо клас
  updateCounter();                        // 4. І знову лічильник
}

function updateCounter() {
  counter.textContent = tasks.filter(t => !t.done).length;
}
```

Зверніть увагу: дані (масив `tasks`) і інтерфейс (DOM) живуть **окремо**, і програміст вручну тримає їх синхронними. Кожна нова функція (видалення, редагування, фільтр «лише невиконані», збереження в `localStorage`) — це ще кілька місць, де треба не забути оновити DOM.

### Чому це стає проблемою

| Проблема | Як проявляється |
|---|---|
| **Розсинхронізація стану й DOM** | Змінили дані, але забули оновити один з елементів — інтерфейс «бреше». |
| **Комбінаторний вибух** | Кожна дія має знати про всі місця, які від неї залежать. При N станах і M елементах кількість зв'язків росте як N × M. |
| **Складність повторного використання** | Шматок інтерфейсу (картка, модальне вікно) важко перенести в інший проєкт: його HTML, CSS і JS розкидані по файлах. |
| **Продуктивність «за замовчуванням»** | Найпростіше рішення — перемалювати все через `innerHTML`, але тоді губляться фокус, введений текст, позиція прокручування, обробники подій. |
| **Безпека** | `innerHTML` з даними користувача відкриває шлях до XSS-атак, якщо забути екранування. |

### Декларативний підхід

**Декларативний** (declarative) код описує, **що** має бути на екрані за поточних даних, а не як до цього дійти. Ідея проста:

```text
UI = f(state)
```

Інтерфейс — це **функція від стану**. Ви пишете, як виглядає список для будь-якого масиву `tasks`, а бібліотека сама з'ясовує, які зміни потрібно внести в DOM. Так само працює SQL: ви пишете `SELECT ... WHERE ...` (що потрібно), а СУБД сама вирішує, як знайти дані.

Порівняйте той самий список у React (синтаксис детально розберемо на наступній лекції):

```jsx title="TodoList.jsx (React)"
function TodoList({ tasks, onToggle }) {
  const left = tasks.filter(t => !t.done).length;

  return (
    <>
      <p>Залишилось: {left}</p>
      <ul>
        {tasks.map(task => (
          <li key={task.id} className={task.done ? 'done' : ''}>
            <label>
              <input type="checkbox" checked={task.done} onChange={() => onToggle(task.id)} />
              {task.text}
            </label>
          </li>
        ))}
      </ul>
    </>
  );
}
```

Тут немає жодного `querySelector`, `append` чи `classList.toggle`. Лічильник неможливо «забути оновити» — він обчислюється з тих самих даних при кожному відображенні.

## 2. MPA і SPA. Способи рендерингу

### Багатосторінковий застосунок (MPA)

**MPA** (Multi-Page Application) — класична модель вебу, з якою ви працювали в модулі PHP. Кожен перехід за посиланням або відправлення форми — це новий HTTP-запит, у відповідь на який сервер повертає **повну HTML-сторінку**. Браузер викидає попередню сторінку і малює нову.

```text
Браузер                         Сервер (PHP)
  │  GET /catalog                  │
  │ ─────────────────────────────► │  формує HTML каталогу
  │ ◄───────────────────────────── │  повна сторінка
  │  клік «Товар 5»                │
  │  GET /product.php?id=5         │
  │ ─────────────────────────────► │  формує HTML товару
  │ ◄───────────────────────────── │  знову повна сторінка (header, footer, стилі...)
```

### Односторінковий застосунок (SPA)

**SPA** (Single-Page Application) завантажує один HTML-документ (часто майже порожній — `<div id="root"></div>`) і JavaScript-бандл. Далі весь інтерфейс будується і змінюється **в браузері**. Під час «переходу на іншу сторінку» JavaScript перемальовує потрібну частину екрана і змінює адресу через History API (`history.pushState`), а з сервера отримує лише **дані** (зазвичай JSON через `fetch`).

```text
Браузер                         Сервер (API)
  │  GET /                         │
  │ ─────────────────────────────► │  index.html + app.js
  │ ◄───────────────────────────── │
  │  JS малює каталог              │
  │  GET /api/products             │
  │ ─────────────────────────────► │
  │ ◄───────────────────────────── │  [{...}, {...}]  (лише JSON)
  │  клік «Товар 5»: URL → /product/5 (без перезавантаження)
  │  GET /api/products/5           │
  │ ─────────────────────────────► │
  │ ◄───────────────────────────── │  {...}
```

Приклади SPA, якими ви користуєтеся щодня: Gmail, Google Maps, Trello, Figma, вебверсії Telegram і Spotify.

### Порівняння MPA і SPA

| Критерій | MPA | SPA |
|---|---|---|
| Перший запуск | Швидкий: браузер одразу отримує готовий HTML | Повільніший: треба завантажити й виконати JS-бандл |
| Подальші переходи | Повне перезавантаження сторінки, «блимання» | Миттєві, без перезавантаження, можна анімувати |
| Навантаження на сервер | Сервер генерує HTML для кожного запиту | Сервер віддає статику та JSON-API |
| SEO | Добре: пошуковик бачить готовий HTML | Складніше: контент з'являється після виконання JS |
| Збереження стану між «сторінками» | Через сесії, cookie, `localStorage` | Природно: стан живе в пам'яті JS |
| Складність | Нижча, логіка здебільшого на сервері | Вища: маршрутизація, стан, кешування — на клієнті |
| Робота без JS | Працює | Зазвичай не працює |
| Типові приклади | Новинні сайти, блоги, інтернет-магазини на CMS | Адмін-панелі, дашборди, редактори, месенджери |

### CSR, SSR, SSG

Сучасні фреймворки поєднують найкраще з обох світів. Варто знати терміни:

| Підхід | Де формується HTML | Коли використовувати |
|---|---|---|
| **CSR** (Client-Side Rendering) | У браузері, JavaScript-ом | Застосунки за логіном, де SEO не важливе: кабінети, адмінки. **Саме так працюватиме наш навчальний магазин.** |
| **SSR** (Server-Side Rendering) | На сервері для кожного запиту, далі в браузері «оживлюється» (hydration) | Сайти, де важливі і SEO, і інтерактивність: магазини, соцмережі. |
| **SSG** (Static Site Generation) | На етапі збирання (build), один раз | Документація, блоги, лендинги. Цей навчальний сайт зібраний саме так (Astro). |
| **RSC** (React Server Components) | Частина компонентів виконується лише на сервері | Новий підхід React 19, доступний у фреймворках (Next.js). |

**Гідратація** (hydration) — процес, коли React у браузері «приєднується» до вже готового серверного HTML: навішує обробники подій і бере DOM під своє керування, не перемальовуючи його.

:::note
SPA і SSR не виключають одне одного. Next.js-застосунок віддає перший екран як готовий HTML (SSR), а далі поводиться як SPA: переходи між сторінками відбуваються без перезавантаження.
:::

## 3. Що таке React

**React** — JavaScript-бібліотека з відкритим кодом для побудови користувацьких інтерфейсів, створена в Facebook (Meta). Офіційний сайт — [react.dev](https://react.dev).

Важливо: React — це саме **бібліотека** (library), а не повноцінний **фреймворк** (framework). Вона відповідає лише за шар відображення: як перетворити дані на інтерфейс і як реагувати на дії користувача. Маршрутизацію, запити до сервера, форми, глобальний стан вирішують окремі бібліотеки або фреймворки, побудовані поверх React (Next.js, React Router).

### Ключові ідеї

1. **Декларативність.** Ви описуєте, як має виглядати інтерфейс за певного стану; React сам оновлює DOM.
2. **Компоненти** (components). Інтерфейс складається з незалежних, повторно використовуваних частин: `Header`, `ProductCard`, `Cart`. Компонент — це звичайна JavaScript-функція, що повертає опис розмітки.
3. **Односпрямований потік даних** (one-way data flow). Дані передаються згори вниз — від батьківського компонента до дочірніх через **пропси** (props). Дочірній компонент не змінює дані батька напряму, а лише «просить» про це, викликаючи передану функцію.
4. **Стан** (state). Дані, що змінюються з часом (вміст кошика, введений текст), зберігаються у стані компонента. Зміна стану — єдиний «законний» спосіб змінити інтерфейс.
5. **«Learn once, write anywhere».** Ті самі знання (компоненти, пропси, стан, хуки) працюють у вебі (`react-dom`), на мобільних пристроях (React Native — модуль 8), у десктопі та навіть у терміналі.

Як це виглядає в дереві компонентів:

```text
App  (стан: products, cart)
├── Header        ← cartCount
├── ProductList   ← products, onAdd
│   ├── ProductCard ← product, onAdd
│   ├── ProductCard
│   └── ProductCard
└── Cart          ← cart, onRemove
```

Дані течуть **вниз** (стрілки ←), а події — **вгору** через функції-колбеки (`onAdd`, `onRemove`).

## 4. Virtual DOM, рендеринг і узгодження

### Чому прямі операції з DOM «дорогі»

DOM — це не просто JavaScript-об'єкти. Зміна DOM може запустити в браузері:

1. **Перерахунок стилів** (recalculate style) — які CSS-правила тепер діють.
2. **Розмітку** (layout, reflow) — обчислення розмірів і позицій елементів.
3. **Малювання** (paint) і **композитинг** (composite) — виведення пікселів на екран.

Якщо в циклі по одному змінювати сотні вузлів і читати їхні розміри між змінами, браузер змушений багато разів робити layout — інтерфейс «гальмує». Звичайні JS-об'єкти, натомість, створюються й порівнюються дуже швидко.

### Що таке Virtual DOM

**Virtual DOM** (віртуальний DOM) — це легке представлення інтерфейсу у вигляді дерева звичайних JavaScript-об'єктів. Коли компонент повертає JSX, насправді він повертає такі об'єкти — **React-елементи** (React elements):

```jsx
<button className="btn" disabled={false}>Купити</button>
```

стає (спрощено):

```js
{
  type: 'button',
  props: {
    className: 'btn',
    disabled: false,
    children: 'Купити'
  }
}
```

React-елемент — це **опис** того, що має бути на екрані, а не сам DOM-вузол. Створити тисячу таких об'єктів — справа мікросекунд.

### Три фази оновлення

Коли стан змінюється, React проходить три кроки:

```text
1. Trigger (запуск)    — setState(...) повідомляє React, що дані змінилися
        │
        ▼
2. Render (рендер)     — React викликає функції компонентів і отримує
                         НОВЕ дерево React-елементів
        │
        ▼  diff: порівняння старого і нового дерева (reconciliation)
        │
3. Commit (фіксація)   — React вносить у справжній DOM ЛИШЕ мінімальний
                         набір змін; браузер перемальовує екран
```

:::caution[Важлива термінологія]
У React слово **«рендер»** означає «виклик функції компонента», а не «малювання на екрані». Компонент може відрендеритися, але DOM при цьому не зміниться, якщо результат такий самий, як минулого разу.
:::

### Алгоритм узгодження (reconciliation)

Порівняти два довільні дерева оптимально — задача складності O(n³), що для тисячі елементів означає мільярд операцій. React використовує **евристичний алгоритм** зі складністю O(n), заснований на двох припущеннях:

1. **Елементи різних типів дають різні дерева.** Якщо на місці `<div>` з'явився `<section>` або `<ProductCard>` змінився на `<Loader>`, React не порівнює їхній вміст — він видаляє старе піддерево (разом зі станом!) і створює нове.
2. **Ключі (`key`) ідентифікують елементи списку між рендерами.** Розробник підказує, який елемент є «тим самим», навіть якщо він змістився в списку.

Приклад: однаковий тип — оновлюються лише змінені атрибути:

```jsx
// Було
<p className="price">100 грн</p>
// Стало
<p className="price sale">80 грн</p>
// DOM: React змінить лише className і текстовий вузол — сам <p> залишиться тим самим
```

### Навіщо потрібні ключі

Уявіть список, на початок якого додали новий елемент:

```text
Було:          Стало:
<li>Хліб</li>  <li>Молоко</li>   ← новий
<li>Сир</li>   <li>Хліб</li>
               <li>Сир</li>
```

Без ключів React порівнює елементи **за позицією**: перший з першим, другий з другим. Йому здається, що «Хліб» змінився на «Молоко», «Сир» — на «Хліб», а «Сир» у кінці — новий. Результат: три зміни замість однієї вставки. Гірше того, якщо в `<li>` був `<input>` з введеним текстом або чекбокс, стан «поїде» не до того елемента.

З ключами React порівнює елементи **за `key`**:

```jsx
<li key="milk">Молоко</li>   {/* новий key — вставити */}
<li key="bread">Хліб</li>    {/* key вже був — залишити */}
<li key="cheese">Сир</li>    {/* key вже був — залишити */}
```

Правила для ключів (детально — на наступній лекції):

- ключ має бути **унікальним серед сусідів** (у межах одного списку);
- ключ має бути **стабільним** — не змінюватися між рендерами; найкраще — `id` з бази даних;
- **не використовуйте** `Math.random()` і, як правило, індекс масиву, якщо список може змінювати порядок.

### Fiber і пріоритети

З React 16 механізм узгодження називається **Fiber**. Його головна особливість — роботу з рендерингу можна **розбити на шматки, призупинити й продовжити**. Завдяки цьому React 18+ підтримує **конкурентний рендеринг** (concurrent rendering): термінові оновлення (введення тексту в поле) обробляються раніше за менш термінові (перебудова великого відфільтрованого списку), і інтерфейс не «замерзає».

Ще одна оптимізація — **групування оновлень** (batching): якщо в одному обробнику кілька разів змінити стан, React виконає лише один рендер.

### Міфи про Virtual DOM

| Твердження | Насправді |
|---|---|
| «Virtual DOM швидший за DOM» | Ні. Додатковий шар порівняння завжди коштує часу. Ідеально написаний вручну код буде швидшим. Перевага React — у тому, що **достатньо швидкий** код виходить «за замовчуванням», без ручної оптимізації кожного оновлення. |
| «React перемальовує всю сторінку» | Ні. React **викликає функції** компонентів, але в DOM вносить лише різницю. |
| «Без Virtual DOM реактивність неможлива» | Ні. Svelte і SolidJS обходяться без нього: компілятор або «сигнали» точково оновлюють DOM. |

Новачкам часто здається, що «треба вивчити все». Ні. Порядок такий:

3. Контекст і власні хуки.

## 7. Перший погляд на React-код

Щоб відчути React «наживо» ще до встановлення інструментів, можна підключити його в HTML-файл через CDN модулів [esm.sh](https://esm.sh). JSX браузер не розуміє, тому тут використано функцію `createElement`, у яку JSX перетворюється під капотом:

```html title="hello-react.html"
<!doctype html>
<html lang="uk">
<head>
  <meta charset="UTF-8">
  <title>Привіт, React</title>
</head>
<body>
  <div id="root"></div>

  <script type="module">
    import { createElement as h, useState } from 'https://esm.sh/react@19';
    import { createRoot } from 'https://esm.sh/react-dom@19/client';

    // Компонент — звичайна функція, що повертає опис інтерфейсу
    function Counter() {
      const [count, setCount] = useState(0);

      return h('div', null,
        h('h1', null, 'Лічильник: ', count),
        h('button', { onClick: () => setCount(count + 1) }, '+1'),
        h('button', { onClick: () => setCount(0) }, 'Скинути')
      );
    }

    // Точка входу: React бере під контроль <div id="root">
    createRoot(document.getElementById('root')).render(h(Counter));
  </script>
</body>
</html>
```

Відкрийте файл через Live Server у VS Code і натисніть кнопки. Що тут відбувається:

1. `createRoot(...)` створює **корінь** React-застосунку в елементі `#root`.
2. `render(h(Counter))` — React викликає функцію `Counter` і отримує дерево React-елементів, створює за ним DOM.
3. Клік викликає `setCount(count + 1)` — це **запуск** (trigger) оновлення.
4. React знову викликає `Counter` (рендер), порівнює нове дерево зі старим і змінює в DOM **лише текстовий вузол** із числом (commit).

Відкрийте DevTools → Elements і поклацайте кнопку: підсвічуватиметься лише змінений текст, а не весь `<div>`.

Той самий компонент у JSX, як ми писатимемо далі:

```jsx title="Counter.jsx"
import { useState } from 'react';

export default function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <h1>Лічильник: {count}</h1>
      <button onClick={() => setCount(count + 1)}>+1</button>
      <button onClick={() => setCount(0)}>Скинути</button>
    </div>
  );
}
```

:::caution
Підключення через CDN підходить лише для експериментів. Реальні проєкти створюються за допомогою збирача (Vite), який перетворює JSX, об'єднує модулі, мінімізує код і забезпечує миттєве оновлення під час розробки. Це — тема практичного заняття.
:::

## Підсумки

- Ручна (імперативна) робота з DOM у великих інтерфейсах призводить до розсинхронізації даних і відображення. Декларативний підхід описує інтерфейс як функцію від стану: **UI = f(state)**.
- **MPA** отримує з сервера повну сторінку на кожен перехід; **SPA** завантажує застосунок один раз і далі обмінюється із сервером лише даними. Існують також SSR, SSG і їхні комбінації.
- **React** — бібліотека для побудови інтерфейсів з компонентів. Ключові ідеї: декларативність, компоненти, односпрямований потік даних, стан.
- **Virtual DOM** — дерево JS-об'єктів (React-елементів). Оновлення проходить фази trigger → render → commit; алгоритм **узгодження** порівнює дерева за типами елементів і ключами та вносить у DOM мінімальні зміни.
- **Ключі** в списках мають бути унікальними серед сусідів і стабільними.
- Екосистема React величезна, але для старту достатньо React + Vite + React Router + Context.

## Контрольні питання

1. Чим імперативний підхід до побудови інтерфейсу відрізняється від декларативного? Наведіть приклад.
2. Що означає формула UI = f(state)?

4. Чим відрізняються CSR, SSR і SSG? Що таке гідратація?
5. Чому React називають бібліотекою, а не фреймворком?
6. Що таке React-елемент? Чим він відрізняється від DOM-вузла?
7. Опишіть фази trigger, render і commit. Чи завжди рендер компонента змінює DOM?
8. На яких двох припущеннях ґрунтується алгоритм узгодження?
9. Навіщо потрібен атрибут `key` і чому не варто використовувати як ключ `Math.random()`?
