## Мета роботи

- Зрозуміти, чим продакшн-середовище (production) відрізняється від середовища розробки (development), і підготувати до нього проєкт.
- Винести паролі та налаштування середовища в `config.local.php`, який не потрапляє в git.
- Вимкнути показ помилок користувачам і налаштувати їх журналювання.
- Написати `.htaccess`: заборона доступу до службових файлів і папок, власні сторінки помилок, заголовки безпеки, перенаправлення на HTTPS.
- Розгорнути «Міні-блог» на безкоштовному хостингу з PHP і MySQL: створити БД, імпортувати схему й дані через phpMyAdmin, завантажити файли через FTP (FileZilla).
- Перевірити роботу сайту і API в інтернеті та пройти підсумковий чек-лист.

## Що потрібно

- Проєкт `mini-blog` у стані після П12: сторінки блогу з користувачами й коментарями, `src/Database.php`, `src/PostRepository.php`, `api/posts.php`, `api-demo.html`, `schema.sql`.
- **FileZilla Client** ([filezilla-project.org](https://filezilla-project.org)) — FTP-клієнт. Завантажуйте лише з офіційного сайту й уважно знімайте позначки з пропозицій встановити сторонні програми в інсталяторі.
- Обліковий запис на безкоштовному хостингу з підтримкою PHP 8.2+ і MySQL (наприклад, InfinityFree або аналогічний сервіс; умови безкоштовних тарифів змінюються, тому перед реєстрацією перевірте актуальні обмеження на сайті хостингу).
- Git і (за бажанням) обліковий запис GitHub.

:::note[Якщо хостинг недоступний]
Якщо з якоїсь причини зареєструватися на хостингу не вдається, виконайте кроки 1–6 і 12 локально, а «продакшн» імітуйте: окрема база `mini_blog_prod`, `config.local.php` з `debug => false` і перевірка `.htaccess` на XAMPP. Повідомте викладача — він підкаже альтернативу.
:::

## Короткі теоретичні відомості

### Види хостингу

| Вид | Що це | Плюси | Мінуси |
|---|---|---|---|
| **Віртуальний (shared) хостинг** | Ваш сайт — одна з сотень папок на спільному сервері з Apache, PHP і MySQL | Дешево або безкоштовно, нічого не треба налаштовувати | Немає SSH/root, обмеження ресурсів, не все можна змінити |
| **VPS** (Virtual Private Server) | Власна віртуальна машина з повним доступом | Повний контроль, будь-яке ПЗ | Адмініструєте самі: оновлення, безпека, резервні копії |
| **PaaS** (Platform as a Service) | Платформа сама збирає й запускає застосунок з git | Зручне розгортання, масштабування | Ціна, прив'язка до платформи |

Для навчального PHP-проєкту найпростіший — віртуальний хостинг: там уже є все те саме, що і в XAMPP.

### Розробка проти продакшну

| | Development (XAMPP) | Production (хостинг) |
|---|---|---|
| Помилки PHP | Показуються на сторінці — так швидше налагоджувати | **Не показуються**, пишуться в журнал |
| Користувач БД | `root` без пароля | Окремий користувач зі складним паролем |
| Хост БД | `127.0.0.1` | Вказаний у панелі (часто окремий сервер, не `localhost`) |
| Протокол | `http://localhost` | `https://ваш-домен` |
| Службові файли | Можна відкрити в браузері | Мають бути **недоступні** ззовні |
| Тестові скрипти | `test-db.php`, `import.php` | Не завантажуються на сервер |

Звідси головний принцип: **код однаковий, конфігурація — різна**. Різниця між середовищами живе в окремому файлі конфігурації, якого немає в репозиторії.

### Корінь документів і FTP

**Корінь документів** (document root) — папка на сервері, вміст якої доступний з вебу. У XAMPP це `htdocs`, на віртуальних хостингах — зазвичай `htdocs` або `public_html` у вашому акаунті. Файл `htdocs/index.php` відкривається за адресою `https://ваш-домен/`.

**FTP** (File Transfer Protocol) — протокол для завантаження файлів на сервер. Класичний FTP передає логін, пароль і файли **відкритим текстом**. Якщо хостинг підтримує **FTPS** (FTP через TLS) або **SFTP** (через SSH) — обирайте їх.

### `.htaccess`

`.htaccess` — файл налаштувань Apache для окремої папки (і всіх вкладених). На віртуальному хостингу це основний спосіб керувати сервером: заборонити доступ, налаштувати перенаправлення, сторінки помилок, заголовки. Вбудований сервер `php -S` файли `.htaccess` **ігнорує** — перевіряйте їх у XAMPP.

## Хід роботи

### Крок 1. Конфігурація поза git: `config.local.php`

Перепишемо `config.php`: він містить **безпечні значення за замовчуванням** для локальної розробки, а якщо поруч лежить `config.local.php` — значення з нього їх перекривають.

```php title="config.php"
<?php
declare(strict_types=1);

// Значення за замовчуванням — для локальної розробки (XAMPP)
$config = [
    'debug' => true,
    'db' => [
        'host'    => '127.0.0.1',
        'port'    => 3306,
        'name'    => 'mini_blog',
        'user'    => 'root',
        'pass'    => '',
        'charset' => 'utf8mb4',
    ],
];

// Налаштування конкретного середовища (паролі!) — у файлі, якого немає в git
$localFile = __DIR__ . '/config.local.php';
if (is_file($localFile)) {
    $config = array_replace_recursive($config, require $localFile);
}

return $config;
```

`array_replace_recursive` замінює лише ті ключі, які є в локальному файлі: можна вказати тільки `db.pass`, а решта залишиться за замовчуванням.

Створіть **приклад** локального файлу — він потрапить у git і підкаже, що треба заповнити на сервері:

```php title="config.local.php.example"
<?php
// Скопіюйте у config.local.php і заповніть даними з панелі хостингу.
// config.local.php НЕ додається в git!
return [
    'debug' => false,
    'db' => [
        'host' => 'sqlXXX.хостинг.example', // хост MySQL з панелі керування
        'name' => 'логін_mini_blog',
        'user' => 'логін',
        'pass' => 'пароль-з-панелі',
    ],
];
```

`Database::connection()` з П12 уже читає `config.php`, тож змінювати клас не потрібно.

### Крок 2. Режим налагодження і журнал помилок

На початку `includes/helpers.php` (одразу після `declare`) додамо функцію доступу до конфігурації і налаштування виведення помилок:

```php title="includes/helpers.php (початок файлу)"
<?php
declare(strict_types=1);

// Значення з config.php (файл читається один раз за запит)
function config(string $key, mixed $default = null): mixed
{
    static $config = null;
    $config ??= require __DIR__ . '/../config.php';
    return $config[$key] ?? $default;
}

// Помилки: у розробці — на екран, на продакшні — лише в журнал
error_reporting(E_ALL);
ini_set('display_errors', config('debug') ? '1' : '0');
ini_set('log_errors', '1');

// На продакшні неперехоплений виняток → журнал + загальна сторінка 500
if (!config('debug')) {
    set_exception_handler(function (Throwable $ex): void {
        error_log((string) $ex);
        http_response_code(500);
        readfile(__DIR__ . '/../errors/500.html');
    });
}

// ...далі is_https(), налаштування сесії, e(), redirect() — без змін
```

Перевірте локально: створіть `config.local.php` з `return ['debug' => false];`, тимчасово зробіть помилку в назві таблиці в `index.php` (`FROM postz`) і відкрийте сторінку. Замість трасування з `SQLSTATE[42S02]` має з'явитися загальна сторінка помилки (її створимо на кроці 4), а текст помилки — у журналі Apache (`C:\xampp\apache\logs\error.log` або `/Applications/XAMPP/logs/error_log`). Поверніть назву таблиці й видаліть локальний `config.local.php` (або поставте в ньому `'debug' => true`).

:::caution[Чому це важливо]
Повідомлення про помилку на продакшні може містити шлях до файлів, ім'я користувача БД, фрагменти SQL-запитів. Для зловмисника це карта вашого застосунку, а для користувача — незрозумілий «технічний сміттєвий текст». Детально — у лекції 13, розділ 10.
:::

### Крок 4. Власні сторінки помилок

Створіть папку `errors/` з трьома статичними сторінками. Вони мають бути простими HTML-файлами без PHP: сторінка 500 показується саме тоді, коли PHP або БД «впали».

```html title="errors/404.html"
<!doctype html>
<html lang="uk">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Сторінку не знайдено — Міні-блог</title>
  <style>
    body { font-family: system-ui, sans-serif; text-align: center; padding: 4rem 1rem; color: #1e293b; }
    h1 { font-size: 4rem; margin: 0; }
  </style>
</head>
<body>
  <h1>404</h1>
  <p>Такої сторінки немає. Можливо, її видалили або адресу введено з помилкою.</p>
  <p><a href="/">← На головну</a></p>
</body>
</html>
```

За тим самим шаблоном створіть `errors/403.html` («Доступ заборонено») і `errors/500.html` («Щось пішло не так. Ми вже знаємо про проблему, спробуйте пізніше»).

### Крок 5. `.htaccess`: захист і налаштування Apache

**Кореневий `.htaccess`:**

```apache title=".htaccess"
# --- Загальне ---
# Не показувати список файлів у папках без index.php
Options -Indexes
DirectoryIndex index.php

# --- Власні сторінки помилок (шлях від кореня домену!) ---
ErrorDocument 403 /errors/403.html
ErrorDocument 404 /errors/404.html
ErrorDocument 500 /errors/500.html

# --- Службові файли в корені недоступні з вебу ---
<FilesMatch "^(config.*\.php|config\.local\.php\.example|schema\.sql|import\.php|test-.*\.php|\.gitignore)$">
    Require all denied
</FilesMatch>

# Приховані файли й папки (.git, .env, .vscode...) — «не існують»
RedirectMatch 404 /\.(git|env|vscode|idea)

# --- Заголовки безпеки (лекція 13) ---
<IfModule mod_headers.c>
    Header always set X-Content-Type-Options "nosniff"
    Header always set X-Frame-Options "DENY"
    Header always set Referrer-Policy "strict-origin-when-cross-origin"
    Header always set Permissions-Policy "camera=(), microphone=(), geolocation=()"
</IfModule>

# --- Перенаправлення на HTTPS: увімкнути ПІСЛЯ того, як запрацює сертифікат (крок 11) ---
# <IfModule mod_rewrite.c>
#     RewriteEngine On
#     RewriteCond %{HTTPS} !=on
#     RewriteRule ^ https://%{HTTP_HOST}%{REQUEST_URI} [L,R=301]
# </IfModule>
```

**Службові папки** закриваємо окремими `.htaccess` з одного рядка. Створіть однаковий файл у кожній з папок `includes/`, `src/` і `data/`:

```apache title="includes/.htaccess (так само src/.htaccess і data/.htaccess)"
Require all denied
```

Перевірте локально в XAMPP:

| Адреса | Очікуваний результат |
|---|---|
| `http://localhost/mini-blog/` | Блог працює як раніше |
| `.../mini-blog/includes/db.php` | 403 |
| `.../mini-blog/src/Database.php` | 403 |
| `.../mini-blog/config.php` | 403 |
| `.../mini-blog/schema.sql` | 403 |
| `.../mini-blog/assets/` | 403 (немає списку файлів) |
| `.../mini-blog/nema-takoi-storinky` | 404 |

:::note[Сторінки помилок локально]
Шляхи `ErrorDocument` вказані від кореня домену (`/errors/404.html`), бо на хостингу блог лежатиме в корені. Локально проєкт у підпапці `/mini-blog/`, тому Apache шукатиме `http://localhost/errors/404.html` і покаже стандартну сторінку. Це нормально; для локальної перевірки можна тимчасово змінити шляхи на `/mini-blog/errors/...`.
:::

:::caution[Помилка 500 після додавання `.htaccess`]
Apache відповідає 500, якщо в `.htaccess` є директива, яку сервер не підтримує. Найчастіше це `php_flag`/`php_value` на хостингах з PHP-FPM — тому ми їх не використовуємо. Якщо сайт «упав» — тимчасово перейменуйте `.htaccess` і повертайте блоки по одному, щоб знайти проблемний.
:::

### Крок 6. Підготовка до завантаження

1. **Видаліть тестові файли**: `test-db.php`, `test-repo.php`, будь-які `phpinfo.php`.
2. **Експортуйте базу.** У локальному phpMyAdmin виберіть базу `mini_blog` → **Експорт** → спосіб **Звичайний** (Custom) → формат SQL. У розділі параметрів **зніміть** позначки з `CREATE DATABASE / USE` (на хостингу база вже матиме інше ім'я). Збережіть файл `mini_blog_data.sql`.

   Якщо переносити дані не потрібно — використаєте `schema.sql` з П9: він створить порожні таблиці.

3. **Визначтеся, що завантажувати.** На сервер потрібні:

   ```text
   ✅ index.php, post.php, create.php, edit.php, delete.php,
      login.php, register.php, logout.php, theme.php, api-demo.html
   ✅ config.php, .htaccess
   ✅ api/, assets/, errors/, includes/, src/  (разом з .htaccess усередині)
   ❌ config.local.php (локальний!) — на сервері буде свій
   ❌ .git/, data/, import.php, schema.sql, *.sql, test-*.php
   ```

### Крок 7. Реєстрація на хостингу і створення сайту

Інтерфейси панелей керування різняться, але кроки однакові:

1. Зареєструйтеся на сайті хостингу (пароль — новий, унікальний; збережіть у менеджері паролів).
2. Створіть **хостинг-акаунт / сайт** і оберіть безкоштовний **піддомен** (наприклад, `prizvyshche-blog.<домен-хостингу>`). Активація може тривати від кількох хвилин до години.
3. У панелі знайдіть і запишіть (вони знадобляться далі):
   - **FTP**: хост, логін, пароль, порт;
   - **MySQL**: розділ «MySQL Databases»;
   - версію PHP (має бути 8.2 або новіша — за потреби змініть у налаштуваннях PHP).

:::caution[Не плутайте паролі]
Пароль від облікового запису на сайті хостингу, пароль FTP / хостинг-акаунта і пароль бази даних — часто **різні**. Перевіряйте, який саме пароль вказаний у відповідному розділі панелі.
:::

### Крок 8. База даних на хостингу

1. У розділі **MySQL Databases** створіть базу. Хостинг зазвичай додає до назви префікс вашого логіна — підсумкове ім'я буде схоже на `логін_mini_blog`.
2. Запишіть параметри підключення, які покаже панель: **хост MySQL** (на багатьох хостингах це окремий сервер на кшталт `sqlNNN.<хостинг>`, а **не** `localhost`), ім'я бази, користувач, пароль.
3. Відкрийте **phpMyAdmin** з панелі, виберіть свою базу ліворуч → вкладка **Імпорт** → виберіть `mini_blog_data.sql` (або `schema.sql`) → **Виконати**.
4. Перевірте, що з'явилися таблиці `users`, `posts`, `comments` і (якщо імпортували дані) ваші пости.

Типові помилки імпорту:

| Помилка | Причина | Рішення |
|---|---|---|
| `#1044 - Access denied for user ... to database 'mini_blog'` | У дампі залишився `CREATE DATABASE` або `USE mini_blog` | Повторіть експорт без цих команд або видаліть рядки з файлу в редакторі |
| `#1215 / errno 150` при створенні FK | Таблиці створюються в неправильному порядку | Використайте `schema.sql` (там правильний порядок) або дамп phpMyAdmin (він вимикає перевірку FK на час імпорту) |
| Кракозябри замість кирилиці | Неправильне кодування файлу або таблиць | Файл — у UTF-8, таблиці — `utf8mb4` |
| Файл завеликий | Обмеження розміру завантаження | Для навчального проєкту не актуально; інакше — імпорт частинами |

### Крок 9. Завантаження файлів через FileZilla

1. Відкрийте FileZilla → **Файл → Менеджер сайтів** (Site Manager) → **Новий сайт**:
   - **Протокол**: FTP (або SFTP, якщо хостинг підтримує);
   - **Хост**: FTP-хост з панелі; **порт**: 21 (для SFTP — 22);
   - **Шифрування**: «Використовувати явний FTP через TLS, якщо доступно»;
   - **Тип входу**: «Звичайний»; **користувач** і **пароль** — FTP-дані з панелі.
2. **З'єднатися.** Ліва панель — ваш комп'ютер, права — сервер.
3. На сервері відкрийте папку `htdocs` (або `public_html`). Видаліть з неї стандартну заглушку хостингу (`index2.html`, `default.php` тощо), якщо вона є.
4. Ліворуч перейдіть у `mini-blog`, виділіть файли й папки зі списку «✅» з кроку 6 і перетягніть у праву панель.
5. Дочекайтеся завершення — внизу у вкладці **Невдалі передачі** має бути 0.

:::tip[Приховані файли]
Файли, що починаються з крапки (`.htaccess`), FileZilla може не показувати на сервері. Увімкніть **Сервер → Примусово показувати приховані файли**. Переконайтеся, що `.htaccess` завантажено і в корінь, і в `includes/`, `src/`.
:::

### Крок 10. `config.local.php` на сервері

Створіть **на своєму комп'ютері в окремій папці** (наприклад, `deploy/`, поза проєктом) файл `config.local.php` з даними хостингу:

```php title="deploy/config.local.php"
<?php
return [
    'debug' => false,
    'db' => [
        'host' => 'sqlNNN.хостинг.example', // з панелі
        'name' => 'логін_mini_blog',
        'user' => 'логін',
        'pass' => 'пароль-бази-з-панелі',
    ],
];
```

Завантажте його через FileZilla в `htdocs/` поруч з `config.php`. Перевірте, що `https://ваш-домен/config.local.php` повертає 403 (правило `config.*\.php` у `.htaccess`) — навіть якби PHP-файл виконався, він нічого не вивів би, але заборона — додатковий рівень захисту.

Відкрийте сайт `http://ваш-піддомен/`. Має з'явитися головна сторінка блогу.

Якщо замість неї — сторінка 500:

1. Тимчасово поставте в `config.local.php` на сервері `'debug' => true` і оновіть сторінку — побачите текст помилки.
2. Найчастіше це `SQLSTATE[HY000] [2002]` (неправильний хост БД) або `[1045] Access denied` (логін/пароль).
3. Виправте і **обов'язково** поверніть `'debug' => false`.

Багато хостингів також мають у панелі розділ з журналом помилок (Error Log) — це правильніший спосіб діагностики.

### Крок 11. HTTPS

1. У панелі хостингу знайдіть розділ **SSL/TLS** (Free SSL, Let's Encrypt) і випустіть безкоштовний сертифікат для свого піддомену. На деяких хостингах для цього треба підтвердити володіння доменом (DNS-запис CNAME/TXT) — дотримуйтеся інструкції панелі. Випуск і активація можуть зайняти від кількох хвилин до кількох годин.
2. Відкрийте `https://ваш-піддомен/` — у рядку адреси має бути значок замка без попереджень.
3. Розкоментуйте в кореневому `.htaccess` блок перенаправлення на HTTPS і завантажте файл знову. Тепер `http://...` автоматично перенаправляється на `https://...` (код 301).
4. Перевірте в DevTools → Application → Cookies: кукі `MINIBLOGSESS` тепер має позначку **Secure** — це спрацювала наша функція `is_https()` з П10.

:::caution[Нескінченне перенаправлення]
На деяких хостингах HTTPS «завершується» на проксі-сервері перед Apache, і змінна `%{HTTPS}` завжди порожня — правило перенаправлятиме по колу (`ERR_TOO_MANY_REDIRECTS`). Тоді замініть умову на `RewriteCond %{HTTP:X-Forwarded-Proto} !https`, а в `is_https()` додайте перевірку `($_SERVER['HTTP_X_FORWARDED_PROTO'] ?? '') === 'https'`. Робіть це лише тоді, коли знаєте, що перед сервером справді стоїть проксі хостингу.
:::

Коли HTTPS працює стабільно, можна додати до `.htaccess` в блок `mod_headers` заголовок HSTS — спочатку з невеликим `max-age`:

```apache
Header always set Strict-Transport-Security "max-age=300"
```

### Крок 12. Перевірка на продакшні

Пройдіть повний сценарій уже на сайті в інтернеті — бажано з телефона через мобільний інтернет (так перевірите, що сайт доступний не лише з вашої мережі):

| Перевірка | Очікуваний результат |
|---|---|
| Головна, пошук, пагінація, сортування | Працюють, кирилиця відображається правильно |
| Реєстрація, вихід, вхід | Працюють; у кукі — `HttpOnly`, `Secure`, `SameSite=Lax` |
| Створення, редагування, видалення поста; коментарі | Працюють; чужий пост — 403 |
| Перемикач теми | Тема зберігається між візитами |
| `https://.../api/posts.php` | JSON зі списком постів |
| `https://.../api-demo.html` | Список і створення поста через API |
| `/includes/helpers.php`, `/src/Database.php`, `/config.php`, `/schema.sql` | 403 або 404 |
| `/.git/config` | 404 |
| `/неіснуюча-сторінка` | Ваша сторінка 404 |
| Тимчасова помилка в коді (на копії файлу) | Загальна сторінка 500, без деталей |
| Заголовки відповіді (DevTools → Network) | `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` |

:::note[Захист від ботів на безкоштовних хостингах]
Деякі безкоштовні хостинги перевіряють відвідувачів через JavaScript і кукі, щоб відсіяти ботів. У браузері сайт і `api-demo.html` працюють, а `curl` чи Postman можуть отримувати замість JSON HTML-сторінку з перевіркою. Це обмеження хостингу, а не помилка вашого API — для тестування через curl використовуйте локальну версію.
:::

### Крок 13. Оновлення сайту і резервні копії

Сайт розгорнуто, але робота з ним триває. Сформуйте для себе правила:

1. **Спочатку локально.** Будь-яку зміну спершу перевіряєте в XAMPP, комітите в git, а потім завантажуєте змінені файли через FileZilla (вона запитає, чи перезаписати — «Перезаписати, якщо джерело новіше»).
2. **Зміни структури БД** (нова таблиця, новий стовпець) виконуйте на сервері через phpMyAdmin тим самим SQL, що й локально, і дописуйте в `schema.sql`.
3. **Резервна копія** перед кожним серйозним оновленням: експорт бази з phpMyAdmin на хостингу + копія папки `htdocs` через FileZilla.
4. **Не редагуйте файли прямо на сервері** — зміни, яких немає в git, буде втрачено при наступному завантаженні.

**Результат роботи:** «Міні-блог» доступний в інтернеті за HTTPS, працює з базою даних хостингу, паролі зберігаються поза git у `config.local.php`, помилки не показуються користувачам, службові файли й папки закриті через `.htaccess`, налаштовано власні сторінки помилок і заголовки безпеки.

Логін і пароль FTP збережіть у **GitHub Secrets**, а не у файлі workflow. Опишіть у звіті, які файли виключено з розгортання і чому.
