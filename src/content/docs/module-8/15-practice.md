## Мета роботи

- Зрозуміти правила версіонування мобільного застосунку і налаштувати автоматичне збільшення номера збірки.
- Зібрати продакшн-версію «Моїх місць» у форматі AAB.
- Підготувати матеріали для сторінки в магазині: іконку, feature graphic, скриншоти, описи українською, політику конфіденційності.
- Пройти шлях публікації в Google Play Console до релізу у внутрішньому тестуванні; ознайомитися з `eas submit` і процесом для iOS (TestFlight).
- Налаштувати OTA-оновлення через `expo-updates` та EAS Update і доставити виправлення без нової збірки.
- Підготувати фінальний звіт і захист проєкту.

## Що потрібно

- Проєкт `my-places` після практичної роботи 7: налаштовані `app.json`, `eas.json`, успішна `preview`-збірка.
- Акаунт на expo.dev, встановлений `eas-cli`.
- Акаунт розробника Google Play Console (одноразовий реєстраційний внесок). Якщо особистого акаунта немає, викладач може додати вас до навчального акаунта, або ви виконуєте кроки до завантаження AAB включно і демонструєте решту за інструкцією та скриншотами.
- Акаунт GitHub (для розміщення політики конфіденційності на GitHub Pages).
- Скриншоти застосунку з телефону (домашнє завдання практичної 7).

## Короткі теоретичні відомості

**Версії.** `version` (`"1.0.0"`) бачить користувач; `android.versionCode` — ціле число, яке Google Play використовує для порівняння збірок: кожен новий завантажений AAB повинен мати більший `versionCode`. В iOS аналог — `ios.buildNumber`. При `"appVersionSource": "remote"` номери збірок зберігаються на сервері EAS, а `"autoIncrement": true` у профілі `production` збільшує їх перед кожною збіркою.

**Треки Google Play.** Внутрішнє тестування (до 100 тестувальників, доступно майже одразу) → закрите тестування → відкрите тестування → продакшн. Для нових особистих акаунтів розробника перед виходом у продакшн обов'язкове закрите тестування з мінімальною кількістю тестувальників протягом визначеного часу — перевіряйте актуальні вимоги в Play Console.

**OTA-оновлення.** Бібліотека `expo-updates` при запуску застосунку перевіряє, чи є на його **каналі** (channel) новий JS-бандл, сумісний за `runtimeVersion`, завантажує його і застосовує при наступному запуску. Так можна виправити помилку в JS без нової збірки і рев'ю магазину; зміни нативного коду так доставити неможливо.

## Хід роботи

### Крок 1. Версіонування

Перевірте `eas.json` з практичної 7: у `cli` має бути `"appVersionSource": "remote"`, а в профілі `production` — `"autoIncrement": true`.

```json title="eas.json (фрагмент)"
{
  "cli": {
    "appVersionSource": "remote"
  },
  "build": {
    "production": {
      "autoIncrement": true
    }
  }
}
```

Правила, яких дотримуємося:

| Що змінилося | `version` | `versionCode` |
| --- | --- | --- |
| Виправлено помилку | `1.0.0` → `1.0.1` | Збільшується автоматично |
| Нова функція без поломки сумісності | `1.0.1` → `1.1.0` | Збільшується автоматично |
| Суттєві зміни, редизайн | `1.1.0` → `2.0.0` | Збільшується автоматично |
| Повторна збірка тієї ж версії (наприклад, виправили іконку) | Не змінюється | Збільшується автоматично |

Корисні команди:

```bash
# переглянути поточний versionCode, збережений на сервері EAS
eas build:version:get -p android

# вручну встановити значення (наприклад, якщо в Play вже є збірка з вищим номером)
eas build:version:set -p android
```

:::note
При першій збірці з `appVersionSource: "remote"` EAS запропонує взяти початкове значення з `app.json` (`android.versionCode`). Далі поле в `app.json` ігнорується — не дивуйтеся, що воно не змінюється. Поле `version` при цьому і надалі береться з `app.json` і змінюється вами вручну.
:::

### Крок 2. Продакшн-збірка AAB

```bash
eas build -p android --profile production
```

На відміну від `preview`, профіль `production` не містить `buildType: "apk"`, тож результатом буде **Android App Bundle** (`.aab`). Збірка підписується тим самим keystore, що був згенерований у практичній 7 (EAS бере його зі сховища облікових даних).

Після завершення завантажте `.aab` зі сторінки збірки на expo.dev — він знадобиться для першого ручного завантаження в Play Console.

:::caution
AAB не можна встановити на телефон напряму — він призначений лише для Google Play. Для ручного тестування продовжуйте використовувати `preview`-збірки (APK).
:::

Перевірте, що збереглася резервна копія ключа підпису:

```bash
eas credentials -p android
```

У меню можна завантажити keystore (`Download existing keystore`). Збережіть його в надійному місці **поза репозиторієм**.

### Крок 3. Матеріали для сторінки в магазині

Підготуйте графіку відповідно до вимог Google Play:

| Матеріал | Вимоги | Примітки |
| --- | --- | --- |
| Іконка застосунку | 512×512 PNG (32-біт), до 1 МБ | Та сама, що `icon.png`, зменшена; без заокруглень і тіней |
| Feature graphic | 1024×500 JPG або PNG без прозорості | Банер угорі сторінки; назва, логотип, фон у кольорах застосунку |
| Скриншоти телефону | Мінімум 2 (рекомендовано 4–8), співвідношення сторін 9:16 або 16:9 | Реальні екрани застосунку: список, деталі, карта, додавання |

Текстові поля сторінки (обмеження — на момент написання):

- **Назва** — до 30 символів;
- **Короткий опис** — до 80 символів;
- **Повний опис** — до 4000 символів.

Зразок текстів:

```text title="store-listing-uk.txt"
Назва:
Мої місця — щоденник подорожей

Короткий опис:
Зберігайте улюблені місця з фото, погодою та позначкою на карті.

Повний опис:
«Мої місця» — простий особистий щоденник місць, які ви відвідали.

Що вміє застосунок:
• додавати місця з назвою, містом і описом;
• фотографувати місце камерою або обирати фото з галереї;
• визначати ваше місцезнаходження та автоматично підставляти місто;
• показувати всі місця на карті та відкривати деталі одним дотиком;
• відображати поточну погоду в місті кожного місця;
• позначати улюблені місця та переглядати їх окремим списком.

Усі ваші записи і фото зберігаються лише на вашому пристрої. Застосунок не потребує
реєстрації і не показує реклами.

Застосунок створено як навчальний проєкт у межах курсу з розробки мобільних
застосунків на React Native.
```

:::tip[Скриншоти]
Для кращого вигляду скриншоти можна розмістити в рамці телефону з коротким підписом над ним («Усі місця на карті»). Але сам вміст має бути справжнім інтерфейсом застосунку — Google відхиляє сторінки з оманливою графікою.
:::

### Крок 4. Політика конфіденційності

Google Play вимагає посилання на політику конфіденційності для застосунків, що запитують чутливі дозволи (геолокація, камера). Політика має бути доступна за публічним URL (не PDF у Google Drive з обмеженим доступом).

Зразок тексту (адаптуйте під свій застосунок):

```md title="privacy-policy.md"
# Політика конфіденційності застосунку «Мої місця»

Дата набрання чинності: 01.12.2026

Застосунок «Мої місця» (далі — Застосунок) розроблено [Ім'я Прізвище] як навчальний проєкт.
Ця політика пояснює, які дані використовує Застосунок.

## Які дані використовуються

- **Геолокація.** За вашим запитом (кнопка «Моє місцезнаходження») Застосунок отримує
  координати пристрою, щоб зберегти розташування місця та визначити назву міста.
- **Камера та фото.** За вашим запитом Застосунок відкриває камеру або галерею, щоб
  додати фото до місця.
- **Записи про місця** (назва, місто, опис, фото, координати) зберігаються лише локально
  на вашому пристрої.

## Передача даних третім сторонам

Для відображення погоди Застосунок надсилає назву міста або координати до сервісу
Open-Meteo (open-meteo.com). Для визначення назви міста за координатами використовуються
системні служби геокодування Android/iOS. Застосунок не продає і не передає ваші дані
іншим особам, не використовує рекламу та аналітику.

## Зберігання і видалення

Дані зберігаються на пристрої, доки ви не видалите місце або сам Застосунок.
Видалення Застосунку повністю видаляє всі збережені записи.

## Діти

Застосунок не призначений спеціально для дітей і свідомо не збирає їхніх даних.

## Контакти

З питань щодо цієї політики пишіть на: [ваш навчальний e-mail]
```

Розміщення на **GitHub Pages**:

1. Створіть публічний репозиторій, наприклад `my-places-privacy` (або використайте папку `docs/` в основному репозиторії проєкту).
2. Додайте файл `index.md` з текстом політики.
3. У репозиторії відкрийте **Settings → Pages**, у полі **Source** оберіть **Deploy from a branch**, гілку `main` і папку `/ (root)` (або `/docs`). Збережіть.
4. За хвилину-дві сторінка буде доступна за адресою `https://<ваш-логін>.github.io/my-places-privacy/`.
5. Відкрийте адресу в режимі інкогніто й переконайтеся, що вона відкривається без входу в акаунт.

:::caution
Політика має відповідати реальній поведінці застосунку і формі **Data safety** у Play Console. Невідповідність — одна з найчастіших причин відхилення.
:::

### Крок 5. Google Play Console: створення застосунку

1. Увійдіть у [Play Console](https://play.google.com/console) і натисніть **Create app** (Створити застосунок).
2. Заповніть:
   - **App name** — «Мої місця — щоденник подорожей»;
   - **Default language** — Українська (uk-UA);
   - **App or game** — App; **Free or paid** — Free;
   - підтвердьте декларації (відповідність правилам для розробників та експортному законодавству США).
3. Відкриється **Dashboard** зі списком завдань **Set up your app**. Пройдіть кожне:

   | Розділ | Що вказати для «Моїх місць» |
   | --- | --- |
   | Privacy policy | URL з GitHub Pages |
   | App access | Увесь функціонал доступний без входу в акаунт |
   | Ads | Застосунок не містить реклами |
   | Content rating | Заповніть анкету IARC: категорія «Утиліти/Продуктивність», насильства, азартних ігор тощо немає → отримаєте рейтинг для всіх віків |
   | Target audience | Вікова група 18+ (або 13+); застосунок не орієнтований на дітей |
   | News app | Ні |
   | Data safety | Див. нижче |
   | Government apps, Financial features, Health | Ні / не застосовується |

4. **Data safety** (форма безпеки даних). Відповідайте чесно, виходячи з того, що робить ваш код:
   - Дані, які залишаються **лише на пристрої** (фото, записи, точні координати місць), за визначенням Google не вважаються «зібраними».
   - Якщо застосунок надсилає координати або назву міста до Open-Meteo, це передача даних за межі пристрою: вкажіть тип **Location → Approximate location**, мету — **App functionality**, передача шифрується (HTTPS), дані не використовуються для реклами.
   - Механізму видалення облікового запису немає, бо немає акаунтів.

5. **Store listing** (Grow → Store presence → Main store listing): вставте назву, короткий і повний опис, завантажте іконку 512×512, feature graphic та скриншоти. Вкажіть категорію (**Travel & Local** або **Lifestyle**) і контактний e-mail.

### Крок 6. Реліз у внутрішнє тестування

1. У меню оберіть **Test and release → Testing → Internal testing**.
2. На вкладці **Testers** створіть список тестувальників (**Create email list**), додайте свій e-mail і e-mail викладача та одногрупників (адреси акаунтів Google).
3. Натисніть **Create new release**.
4. Підтвердьте використання **Play App Signing** (Google зберігатиме ключ застосунку, а ваш keystore з EAS стане ключем завантаження).
5. Завантажте `.aab` з Кроку 2 у блок **App bundles**. Play Console перевірить `package`, `versionCode` і підпис.
6. **Release name** заповниться автоматично (`versionCode (version)`), наприклад `2 (1.0.0)`.
7. **Release notes** — текст «Що нового» в тегах мови:

   ```text
   <uk-UA>
   Перша тестова версія: місця з фото, геолокацією, погодою та картою.
   </uk-UA>
   ```

8. Натисніть **Next**, перегляньте попередження (warnings можна ігнорувати, errors — ні) і **Save and publish** / **Start rollout to Internal testing**.
9. На вкладці **Testers** скопіюйте посилання **Join on the web / Copy link** і надішліть тестувальникам. Після прийняття запрошення застосунок стає доступним для встановлення з Google Play на їхніх телефонах.

:::note
Перший реліз у внутрішнє тестування зазвичай стає доступним за кілька хвилин, хоча Google може виконувати перевірку довше. Продакшн-реліз завжди проходить рев'ю, яке може тривати від кількох годин до кількох днів.
:::

### Крок 7. Автоматичне завантаження через `eas submit`

Ручне завантаження AAB незручне, коли релізів багато. `eas submit` завантажує збірку в Play Console з командного рядка. Для цього потрібен **ключ сервісного акаунта Google** (service account key).

:::caution[Перше завантаження — вручну]
Google Play API не дозволяє завантажити найпершу збірку нового застосунку. Тому перший AAB завжди завантажують вручну через Play Console (Крок 6), а `eas submit` використовують для наступних.
:::

Огляд налаштування:

1. У [Google Cloud Console](https://console.cloud.google.com) створіть проєкт (або використайте існуючий) і увімкніть **Google Play Android Developer API**.
2. Створіть **Service account** (IAM & Admin → Service accounts) та згенеруйте для нього **ключ у форматі JSON**.
3. У Play Console відкрийте **Users and permissions → Invite new users**, вкажіть e-mail сервісного акаунта і надайте права на керування релізами для вашого застосунку.
4. Збережіть JSON-файл у корені проєкту і **обов'язково** додайте його в `.gitignore`:

   ```bash title=".gitignore (додати)"
   google-service-account.json
   ```

   Альтернатива — завантажити ключ у EAS (`eas credentials` → Google Service Account), тоді файл у проєкті взагалі не потрібен.

5. Налаштуйте профіль submit:

   ```json title="eas.json (фрагмент)"
   {
     "submit": {
       "production": {
         "android": {
           "serviceAccountKeyPath": "./google-service-account.json",
           "track": "internal"
         }
       }
     }
   }
   ```

6. Після наступної продакшн-збірки завантажте її:

   ```bash
   # завантажити останню продакшн-збірку
   eas submit -p android --latest

   # або зібрати і одразу відправити в магазин
   eas build -p android --profile production --auto-submit
   ```

### Крок 8. iOS і TestFlight (огляд)

Публікація для iOS технічно схожа, але має свої передумови:

1. Членство в **Apple Developer Program** (щорічна підписка). Без нього неможливо встановити збірку на реальний iPhone поза Expo Go чи опублікувати застосунок.
2. `eas build -p ios --profile production` — EAS запропонує увійти в акаунт Apple і **сам створить** сертифікат для розповсюдження (distribution certificate) та профіль забезпечення (provisioning profile). Mac для цього не потрібен.
3. `eas submit -p ios` завантажує збірку в **App Store Connect** (EAS може автоматично створити запис застосунку з `ios.bundleIdentifier`).
4. Збірка з'являється в **TestFlight**: внутрішні тестувальники (члени команди) отримують її одразу, зовнішні — після короткої бета-перевірки Apple.
5. Для публікації в App Store заповнюють сторінку (опис, скриншоти для потрібних розмірів екранів, політика конфіденційності, розділ App Privacy) і надсилають на **App Review**. Рецензенти вручну перевіряють застосунок, зокрема відповідність текстів дозволів (`NSLocationWhenInUseUsageDescription`, `NSCameraUsageDescription`) реальному використанню.

### Крок 9. OTA-оновлення: встановлення `expo-updates`

```bash
npx expo install expo-updates
eas update:configure
```

Команда `eas update:configure` додає в `app.json` адресу сервера оновлень і `runtimeVersion`, а в `eas.json` — канали для профілів збірки. Перевірте результат:

```json title="app.json (фрагмент)"
{
  "expo": {
    "runtimeVersion": {
      "policy": "appVersion"
    },
    "updates": {
      "url": "https://u.expo.dev/<ваш-project-id>"
    }
  }
}
```

```json title="eas.json (фрагмент)"
{
  "build": {
    "preview": {
      "distribution": "internal",
      "channel": "preview",
      "android": { "buildType": "apk" }
    },
    "production": {
      "autoIncrement": true,
      "channel": "production"
    }
  }
}
```

Що означають ці поля:

- **channel** — «адреса», за якою збірка шукає оновлення. Збірка з профілем `production` слухає канал `production`, з профілем `preview` — канал `preview`.
- **runtimeVersion** з політикою `appVersion` — оновлення отримують лише збірки з тим самим `version`. Коли ви додаєте нативну бібліотеку, ви підвищуєте `version` і робите нову збірку — старі збірки не отримають несумісний JS-код.

:::danger[Потрібна нова збірка]
`expo-updates` — нативний модуль, а канал записується в застосунок під час збірки. Збірки, зроблені до цього кроку, **не вміють** отримувати оновлення. Зробіть нову збірку:

```bash
eas build -p android --profile preview
```

і встановіть цей APK на телефон.
:::

### Крок 10. Публікація оновлення

1. Внесіть помітну зміну в JS-код, наприклад змініть текст порожнього списку в `screens/PlacesScreen.js` або колір кнопки в `constants/theme.js`.
2. Опублікуйте оновлення на канал, який слухає встановлена збірка:

   ```bash
   eas update --channel preview --message "Змінено текст порожнього списку"
   ```

   Для продакшн-збірок з Google Play — відповідно `--channel production`.

3. На телефоні повністю закрийте застосунок і відкрийте знову. За замовчуванням `expo-updates` перевіряє оновлення під час запуску і завантажує його у фоні, а застосовує **при наступному запуску**. Тож закрийте й відкрийте застосунок ще раз — зміна має з'явитися.
4. Перегляньте історію оновлень на expo.dev (розділ **Updates**) або командою:

   ```bash
   eas update:list
   ```

Якщо оновлення виявилося з помилкою, можна повторно опублікувати попередню робочу версію (`eas update:republish`) або просто виправити код і випустити нове оновлення.

Необов'язково — ручна перевірка оновлень з кнопкою в застосунку:

```jsx title="components/UpdateChecker.js"
import { useEffect } from 'react';
import { Alert } from 'react-native';
import * as Updates from 'expo-updates';

export default function UpdateChecker() {
  useEffect(() => {
    // у режимі розробки (Expo Go, dev client) оновлення не працюють
    if (__DEV__) return;

    (async () => {
      try {
        const update = await Updates.checkForUpdateAsync();
        if (update.isAvailable) {
          await Updates.fetchUpdateAsync();
          Alert.alert('Доступне оновлення', 'Перезапустити застосунок зараз?', [
            { text: 'Пізніше', style: 'cancel' },
            { text: 'Перезапустити', onPress: () => Updates.reloadAsync() },
          ]);
        }
      } catch {
        // немає мережі або сервер недоступний — просто працюємо з поточною версією
      }
    })();
  }, []);

  return null;
}
```

Додайте `<UpdateChecker />` всередину `App.js` (наприклад, поруч з `AppNavigator` в `NavigationContainer`).

### Крок 11. Що можна і що не можна доставити через OTA

| Можна через `eas update` | Потрібна нова збірка (`eas build`) і реліз у магазині |
| --- | --- |
| Виправлення помилок у JS-коді | Встановлення/оновлення бібліотеки з нативним кодом (`npx expo install` нового модуля) |
| Нові екрани й компоненти на основі вже наявних модулів | Зміна дозволів і config plugins в `app.json` |
| Зміна стилів, текстів, кольорів | Нова іконка, splash, назва застосунку, `android.package` |
| Зображення та шрифти в бандлі | Оновлення Expo SDK / React Native |
| Зміна логіки роботи з API | Зміна `version` при політиці `appVersion` |

:::caution[Правила магазинів]
Google Play і App Store дозволяють OTA-оновлення JS для виправлень і покращень, але забороняють через них суттєво змінювати призначення застосунку в обхід рев'ю. Великі зміни функціоналу випускайте як нову версію через магазин.
:::

### Крок 12. Фінальний чек-лист проєкту

Перед захистом перевірте:

- [ ] Застосунок запускається без попереджень і помилок у консолі (`npx expo-doctor` без критичних зауважень).
- [ ] Працюють усі функції: список, деталі, додавання, видалення, улюблені, погода, збереження після перезапуску.
- [ ] Геолокація, камера, галерея, карта працюють у власній збірці; відмова в дозволах обробляється коректно.
- [ ] `PlaceCard` загорнуто в `memo`, обробники стабільні, `FlatList` налаштовано; є виміри «до/після».
- [ ] `app.json`: назва «Мої місця», власна іконка, adaptive icon, splash, унікальний `android.package`, тексти дозволів українською.
- [ ] `eas.json`: профілі `development`, `preview`, `production` з каналами.
- [ ] Є APK (`preview`) і AAB (`production`); keystore збережено в резервній копії.
- [ ] Сторінка в магазині заповнена, політика конфіденційності доступна за публічним URL.
- [ ] Реліз у внутрішньому тестуванні (або завантажений AAB і скриншоти кроків).
- [ ] Хоча б одне OTA-оновлення успішно доставлено на телефон.
- [ ] Секрети (ключ сервісного акаунта, keystore) **не** потрапили в репозиторій; ключ Google Maps обмежено пакетом.
- [ ] `README.md` у репозиторії: опис, скриншоти, як запустити (`npm install`, `npx expo start`), посилання на APK.

### Крок 13. Звіт і захист проєкту

Рекомендована структура звіту за модулем:

1. **Титульна сторінка** — назва застосунку, автор, група.
2. **Опис застосунку** — призначення, цільова аудиторія, перелік функцій.
3. **Технології** — Expo, React Navigation, AsyncStorage, Open-Meteo, `expo-location`, `expo-image-picker`, `react-native-maps`, EAS; обґрунтування вибору бібліотек.
4. **Архітектура** — структура папок (`components/`, `screens/`, `navigation/`, `context/`, `services/`, `hooks/`), схема навігації, потік даних через `PlacesContext`.
5. **Ключові фрагменти коду** — 3–5 фрагментів з поясненнями (контекст, робота з дозволами, карта, мемоізація).
6. **Оптимізація** — таблиця вимірювань «до/після», скриншоти Profiler.
7. **Збірка і публікація** — конфігурація `app.json`/`eas.json`, скриншоти сторінок збірок на expo.dev, сторінки в Play Console, релізу у внутрішньому тестуванні, OTA-оновлення.
8. **Висновки** — що вдалося, що ні, які проблеми виникали і як їх розв'язано, ідеї розвитку.

Захист (5–7 хвилин):

- демонстрація застосунку на телефоні, встановленого з APK або Google Play: додавання місця з фото й геолокацією, карта, улюблені, офлайн-збереження;
- демонстрація OTA-оновлення наживо або запис екрана;
- відповіді на 2–3 питання за кодом і контрольними питаннями модуля.

## Підсумок модуля

Протягом модуля «React Native» ви пройшли повний цикл створення мобільного застосунку — від порожнього проєкту до релізу в магазині:

- **Основи.** Як влаштований React Native і чим він відрізняється від React для вебу: нативні компоненти (`View`, `Text`, `Image`, `Pressable`), стилі через `StyleSheet` і Flexbox, Expo та Expo Go для швидкого старту.
- **Компоненти та стан.** Функціональні компоненти, хуки, контрольовані поля вводу, списки `FlatList`, повторно використовувані компоненти (`PlaceCard`, `AddPlaceForm`) і тема застосунку.
- **Дані.** Збереження локально через AsyncStorage, робота з мережею (Open-Meteo), власні хуки (`useWeather`), глобальний стан через Context (`PlacesContext`).
- **Навігація.** React Navigation: native stack, нижні вкладки, модальні екрани, передача параметрів між екранами.
- **Можливості пристрою.** Екосистема бібліотек і вибір пакетів, модель дозволів, геолокація, камера й галерея, нативні карти, config plugins, Expo Go проти development build.
- **Якість і продуктивність.** Потоки JS/UI і бюджет кадру, мемоізація, оптимізація списків і зображень, профілювання в React Native DevTools.
- **Випуск.** Налаштування `app.json`, EAS Build (APK і AAB), підписування та версіонування, підготовка сторінки в магазині та політики конфіденційності, Google Play Console, `eas submit`, OTA-оновлення через EAS Update.

Результат модуля — застосунок «Мої місця», який можна встановити на телефон і показати у своєму портфоліо. Ті самі принципи й інструменти застосовуються в реальних комерційних проєктах на React Native.
