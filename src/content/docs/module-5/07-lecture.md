## Мета заняття

- Зрозуміти, що таке побічні ефекти (side effects) і чому їх не можна виконувати під час рендеру.
- Опанувати хук `useEffect`: коли він виконується, як працює масив залежностей.
- Навчитися писати функцію очищення (cleanup) для таймерів, підписок і слухачів подій.
- Пояснити, чому в режимі розробки зі StrictMode ефекти виконуються двічі, і як писати ефекти, стійкі до цього.
- Правильно завантажувати дані в ефекті: стани завантаження і помилки, стан гонитви (race condition), `AbortController`.
- Розпізнавати ситуації, коли ефект не потрібен («You Might Not Need an Effect»).

## 1. Чисті рендери і побічні ефекти

На лекції 2 ми встановили правило: **компонент має бути чистою функцією**. Під час рендеру він лише обчислює JSX з пропсів і стану. Але реальний застосунок мусить взаємодіяти із зовнішнім світом:

- завантажувати дані з сервера;
- встановлювати таймери (`setInterval`);
- підписуватися на події `window` (`resize`, `scroll`, `keydown`);
- змінювати `document.title`;
- працювати з `localStorage`;
- підключатися до WebSocket-чату;
- керувати сторонніми бібліотеками (карти, графіки), що працюють з DOM напряму.

Усе це — **побічні ефекти** (side effects): дії, що виходять за межі обчислення результату функції.

Де їх виконувати? Є два місця:

| Місце | Коли | Приклад |
|---|---|---|
| **Обробник події** | Ефект спричинений конкретною дією користувача | Клік «Купити» → `fetch('/api/orders', { method: 'POST' })` |
| **`useEffect`** | Ефект спричинений самим фактом відображення компонента — потрібно **синхронізуватися** із зовнішньою системою | Компонент чату на екрані → має бути підключення до сервера; змінився `userId` → треба завантажити інший профіль |

Якщо ефект можна виконати в обробнику — виконуйте в обробнику. `useEffect` — для синхронізації з тим, що знаходиться **поза React**.

### Чому не в тілі компонента

```jsx
function Clock() {
  const [time, setTime] = useState(new Date());

  // ❌ Під час КОЖНОГО рендеру створюється новий інтервал.
  // Кожен інтервал викликає setTime → новий рендер → ще один інтервал...
  setInterval(() => setTime(new Date()), 1000);

  return <p>{time.toLocaleTimeString('uk-UA')}</p>;
}
```

Через кілька секунд працюватимуть сотні інтервалів, а сторінка «зависне». Рендер може виконуватися багато разів і в непередбачуваний момент — тому побічні ефекти в ньому заборонені.

## 2. Хук `useEffect`: синтаксис і момент виконання

```jsx
import { useEffect } from 'react';

useEffect(() => {
  // код ефекту

  return () => {
    // необов'язкова функція очищення
  };
}, [залежності]);
```

**`useEffect`** приймає функцію ефекту і (необов'язково) масив залежностей. React виконує ефект **після того, як зміни зафіксовано в DOM і браузер намалював екран**:

```text
Рендер (виклик компонента) → Commit (оновлення DOM) → Малювання на екрані → useEffect
```

Тобто користувач спочатку бачить результат рендеру, а потім виконується ефект. Це гарантує, що ефект не гальмує відображення, і що в момент виконання DOM уже оновлено.

Найпростіший приклад — синхронізація заголовка вкладки зі станом:

```jsx
import { useState, useEffect } from 'react';

function UnreadCounter() {
  const [unread, setUnread] = useState(0);

  useEffect(() => {
    document.title = unread > 0 ? `(${unread}) Повідомлення` : 'Повідомлення';
  }, [unread]);

  return <button onClick={() => setUnread((n) => n + 1)}>Нове повідомлення</button>;
}
```

## 3. Масив залежностей

Другий аргумент визначає, **коли** React повторно виконує ефект.

| Запис | Коли виконується ефект | Типове використання |
|---|---|---|
| `useEffect(fn)` — без масиву | Після **кожного** рендеру | Майже ніколи не потрібно |
| `useEffect(fn, [])` — порожній масив | Лише після **першого** рендеру (монтування) | Підписка на подію `window`, одноразове завантаження |
| `useEffect(fn, [a, b])` | Після першого рендеру і щоразу, коли змінилося `a` **або** `b` | Завантаження даних за `id`, синхронізація з пропсом |

React порівнює кожну залежність з її значенням у попередньому рендері через `Object.is` (для примітивів — за значенням, для об'єктів і функцій — за посиланням).

### Що має бути в залежностях

**Правило:** у масиві залежностей мають бути **всі реактивні значення**, які використовуються всередині ефекту. Реактивні значення — це пропси, стан і все, що обчислюється з них у тілі компонента.

```jsx
function ProfileTitle({ firstName, lastName }) {
  const fullName = `${firstName} ${lastName}`;

  useEffect(() => {
    document.title = fullName;
  }, [fullName]); // ✅ fullName використовується — fullName у залежностях
}
```

Залежності **не обираються** довільно — вони визначаються кодом ефекту. Якщо пропустити залежність, ефект працюватиме з **застарілим** значенням (stale closure).

Не потрібно додавати в залежності:

- функції-сеттери стану (`setCount`) — React гарантує, що вони стабільні;
- значення, оголошені **поза** компонентом (константи модуля, імпорти);
- `ref.current`.

:::tip[ESLint допоможе]
Шаблон Vite містить плагін `eslint-plugin-react-hooks` з правилом `react-hooks/exhaustive-deps`. Воно підсвічує пропущені залежності прямо у VS Code. **Не вимикайте це правило** і не ігноруйте його попередження — майже завжди воно вказує на справжню помилку.
:::

### Об'єкти й функції як залежності

```jsx
function SearchResults({ query }) {
  const options = { query, limit: 10 };   // новий об'єкт при КОЖНОМУ рендері

  useEffect(() => {
    fetchResults(options);
  }, [options]); // ⚠️ Ефект виконується після кожного рендеру: посилання щоразу інше
}
```

Рішення — створити об'єкт **всередині** ефекту і залежати від примітивів:

```jsx
useEffect(() => {
  const options = { query, limit: 10 };
  fetchResults(options);
}, [query]); // ✅ рядок порівнюється за значенням
```

Те саме з функціями: якщо функція потрібна лише ефекту — оголосіть її всередині ефекту.

## 4. Очищення ефекту

Багато ефектів щось **створюють**: інтервал, підписку, з'єднання. Якщо їх не прибрати, вони продовжать працювати після того, як компонент зникне з екрана — це **витік пам'яті** (memory leak) і джерело дивних помилок.

Функція, яку повертає ефект, — **функція очищення** (cleanup). React викликає її:

1. **перед повторним виконанням** ефекту (коли змінилися залежності) — щоб «прибрати» попередній;
2. **при розмонтуванні** (unmount) — коли компонент зникає з екрана.

### Таймер

```jsx
function Clock() {
  const [time, setTime] = useState(() => new Date());

  useEffect(() => {
    const id = setInterval(() => setTime(new Date()), 1000);
    return () => clearInterval(id);   // очищення
  }, []);

  return <p className="clock">{time.toLocaleTimeString('uk-UA')}</p>;
}
```

### Слухач події window

```jsx
function WindowWidth() {
  const [width, setWidth] = useState(window.innerWidth);

  useEffect(() => {
    function handleResize() {
      setWidth(window.innerWidth);
    }
    window.addEventListener('resize', handleResize);
    return () => window.removeEventListener('resize', handleResize);
  }, []);

  return <p>Ширина вікна: {width}px {width < 768 && '(мобільний вигляд)'}</p>;
}
```

Для `removeEventListener` потрібне **те саме посилання** на функцію, що й для `addEventListener`, — тому обробник оголошено в ефекті як іменовану функцію.

### Підключення, що залежить від пропса

```jsx
function ChatRoom({ roomId }) {
  useEffect(() => {
    const connection = createConnection(roomId);
    connection.connect();
    console.log(`✅ Підключено до кімнати ${roomId}`);

    return () => {
      connection.disconnect();
      console.log(`❌ Відключено від кімнати ${roomId}`);
    };
  }, [roomId]);

  return <h2>Кімната: {roomId}</h2>;
}
```

Що відбувається, коли користувач перемикає кімнату `general` → `travel`:

```text
Монтування з roomId='general'   → ✅ Підключено до кімнати general
Зміна roomId на 'travel':
   очищення старого ефекту       → ❌ Відключено від кімнати general
   виконання нового ефекту       → ✅ Підключено до кімнати travel
Розмонтування                    → ❌ Відключено від кімнати travel
```

### Що потребує очищення

| Ефект | Очищення |
|---|---|
| `setInterval` / `setTimeout` | `clearInterval` / `clearTimeout` |
| `addEventListener` | `removeEventListener` з тим самим обробником |
| WebSocket, EventSource, підключення | `close()`, `disconnect()` |
| Підписка на сторонню бібліотеку | Відповідний метод `unsubscribe()` |
| `fetch` | `AbortController.abort()` або прапорець ігнорування (розділ 6) |
| Анімація, сторонній віджет | Повернути початковий стан, `destroy()` |
| `document.title = ...` | Зазвичай не потрібне |

## 5. Життєвий цикл ефекту і StrictMode

### Думайте синхронізацією, а не життєвим циклом

У класових компонентах були методи `componentDidMount`, `componentDidUpdate`, `componentWillUnmount`. Спокусливо вважати, що `useEffect(fn, [])` — це «didMount». Але правильніша модель інша: **ефект описує, як синхронізувати компонент із зовнішньою системою для поточних пропсів і стану**, а очищення — як цю синхронізацію припинити. React сам вирішує, коли запустити і зупинити синхронізацію. Кожен ефект має бути здатен запускатися і зупинятися **скільки завгодно разів**.

### Подвійний виклик у StrictMode

У проєкті Vite `App` обгорнутий у `<StrictMode>`. У **режимі розробки** React після монтування компонента **одразу розмонтовує і монтує його знову**, тобто послідовність така:

```text
ефект → очищення → ефект
```

Для `ChatRoom` у консолі ви побачите:

```text
✅ Підключено до кімнати general
❌ Відключено від кімнати general
✅ Підключено до кімнати general
```

Це не баг, а **навмисна перевірка**: React імітує ситуацію, коли користувач пішов зі сторінки і повернувся. Якщо ефект написано правильно (з очищенням), користувач не помітить різниці: в результаті — одне активне з'єднання. Якщо очищення забули — побачите два з'єднання, два інтервали, подвійне додавання елементів. StrictMode «виносить» таку помилку на поверхню одразу.

| Ситуація | Що робити |
|---|---|
| Двічі підписується / підключається | Додати функцію очищення |
| Двічі виконується `fetch` | Нормально в розробці; додати `AbortController` або прапорець ігнорування, щоб врахувався лише останній |
| Двічі надсилається аналітика / POST-запит | Такий код має бути в обробнику події, а не в ефекті |
| Хочеться «вимкнути подвійний виклик» | **Не прибирайте StrictMode** — виправте ефект. У production-збірці подвійного виклику немає |

## 6. Завантаження даних в ефекті

Найпоширеніше використання `useEffect` у навчальних і невеликих проєктах — завантаження даних, коли компонент з'являється на екрані або змінюється параметр. Приклад: профіль користувача з тестового API JSONPlaceholder.

### Базова версія з трьома станами

```jsx
import { useState, useEffect } from 'react';

function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    // Функцію ефекту не можна робити async — оголошуємо async-функцію всередині
    async function loadUser() {
      setLoading(true);
      setError(null);
      try {
        const res = await fetch(`https://jsonplaceholder.typicode.com/users/${userId}`);
        if (!res.ok) throw new Error(`Помилка ${res.status}`);
        const data = await res.json();
        setUser(data);
      } catch (err) {
        setError(err.message);
      } finally {
        setLoading(false);
      }
    }

    loadUser();
  }, [userId]);

  if (loading) return <p>Завантаження…</p>;
  if (error) return <p className="error">Не вдалося завантажити: {error}</p>;

  return (
    <article>
      <h2>{user.name}</h2>
      <p>{user.email} · {user.company.name}</p>
    </article>
  );
}
```

Зверніть увагу:

- `fetch` **не відхиляє** проміс при HTTP-помилках 404/500 — тому перевіряємо `res.ok` і кидаємо помилку вручну;
- три стани — `loading`, `error`, дані — покривають усі варіанти відображення;
- `useEffect(async () => {...})` писати **не можна**: async-функція повертає проміс, а React чекає від ефекту функцію очищення або нічого.

### Проблема: стан гонитви (race condition)

Нехай користувач швидко перемикає профілі: `userId` 1 → 2 → 3. Запускаються три запити. Мережа непередбачувана: відповідь для користувача 2 може прийти **останньою** — і на екрані з `userId = 3` з'явиться профіль користувача 2.

```text
час →
запит 1  ├──────┤ setUser(1)
запит 2  ├─────────────────────┤ setUser(2)   ← прийшов останнім і перезаписав!
запит 3  ├────────┤ setUser(3)
екран: userId=3, але показано користувача 2 ❌
```

### Рішення 1: прапорець ігнорування

```jsx
useEffect(() => {
  let ignore = false;

  async function loadUser() {
    const res = await fetch(`https://jsonplaceholder.typicode.com/users/${userId}`);
    const data = await res.json();
    if (!ignore) setUser(data);    // застарілу відповідь ігноруємо
  }

  loadUser();
  return () => { ignore = true; };  // очищення: «цей запит більше не актуальний»
}, [userId]);
```

Коли `userId` змінюється, очищення попереднього ефекту встановлює його `ignore = true`, і відповідь старого запиту вже не потрапить у стан.

### Рішення 2: AbortController

**`AbortController`** — стандартний вебінтерфейс для скасування асинхронних операцій. Його `signal` передають у `fetch`; виклик `abort()` перериває запит, і `fetch` відхиляє проміс з помилкою `AbortError`. Перевага над прапорцем — запит справді скасовується і не витрачає мережу.

```jsx
useEffect(() => {
  const controller = new AbortController();

  async function loadUser() {
    setLoading(true);
    setError(null);
    try {
      const res = await fetch(`https://jsonplaceholder.typicode.com/users/${userId}`, {
        signal: controller.signal,
      });
      if (!res.ok) throw new Error(`Помилка ${res.status}`);
      setUser(await res.json());
      setLoading(false);
    } catch (err) {
      if (err.name === 'AbortError') return; // скасування — не помилка, нічого не робимо
      setError(err.message);
      setLoading(false);
    }
  }

  loadUser();
  return () => controller.abort();           // очищення: скасувати запит
}, [userId]);
```

Чому `setLoading(false)` не у `finally`: якщо запит скасовано, значить, уже стартував новий, і він сам керує станом завантаження. Інакше скасований запит міг би «вимкнути» індикатор, поки новий ще триває.

У StrictMode тепер видно у вкладці Network: перший запит позначений як `(canceled)`, другий — успішний. Саме так і має бути.

### Чому в реальних проєктах беруть бібліотеки

Ручне завантаження в ефекті не вирішує багатьох задач: кешування (повернулися на сторінку — дані знову вантажаться), повторні спроби, оновлення у фоні, дедуплікація однакових запитів. Тому в продакшені використовують **TanStack Query**, **SWR** або механізми завантаження фреймворків (React Router loaders, Next.js). Але розуміти, як це працює «вручну», необхідно — на практичній 11 ми саме так підключимо магазин до API, а на практичній 13 загорнемо цю логіку у власний хук `useFetch`.

## 7. Коли ефект не потрібен

Офіційна документація React має окрему статтю [«You Might Not Need an Effect»](https://react.dev/learn/you-might-not-need-an-effect). Ефекти — «аварійний вихід» із React-світу; зайві ефекти роблять код повільнішим (додаткові рендери) і заплутаним. Розглянемо типові випадки.

### Випадок 1. Обчислення похідних даних

```jsx
// ❌ Зайвий стан і зайвий ефект: два рендери замість одного
const [items, setItems] = useState([]);
const [total, setTotal] = useState(0);
useEffect(() => {
  setTotal(items.reduce((s, i) => s + i.price, 0));
}, [items]);

// ✅ Обчислюємо під час рендеру
const total = items.reduce((s, i) => s + i.price, 0);
```

Те саме для фільтрації і сортування списку за пошуковим запитом: `const visible = items.filter(...)` прямо в тілі компонента. Якщо обчислення справді дороге — є хук `useMemo` (або React Compiler зробить це автоматично).

### Випадок 2. Реакція на дію користувача

```jsx
// ❌ Ефект «стежить» за станом, щоб зрозуміти, що сталося
const [submitted, setSubmitted] = useState(false);
useEffect(() => {
  if (submitted) {
    fetch('/api/feedback', { method: 'POST', body: JSON.stringify(form) });
    showToast('Дякуємо!');
  }
}, [submitted]);

// ✅ Логіка — в обробнику події, де відомо, що саме сталося
function handleSubmit(e) {
  e.preventDefault();
  fetch('/api/feedback', { method: 'POST', body: JSON.stringify(form) });
  showToast('Дякуємо!');
}
```

Питання-тест: **«Чому виконується цей код?»** Якщо відповідь «бо користувач натиснув кнопку» — це обробник події. Якщо «бо компонент з'явився на екрані / змінився параметр, і треба синхронізуватися з зовнішньою системою» — це ефект.

### Випадок 3. Скидання стану при зміні пропса

```jsx
// ❌ Скидаємо коментар у ефекті: спершу рендер зі старим текстом, потім ще один
function CommentBox({ postId }) {
  const [text, setText] = useState('');
  useEffect(() => { setText(''); }, [postId]);
  // ...
}

// ✅ Даємо компоненту key — React створить новий екземпляр зі свіжим станом
<CommentBox key={postId} postId={postId} />
```

Тут використано знання з лекції 1: компонент з іншим `key` для React — інший компонент, його стан створюється заново.

### Випадок 4. Ланцюжки ефектів

```jsx
// ❌ Ефект змінює стан, що запускає інший ефект, що змінює стан...
useEffect(() => { if (card) setGoldCount((c) => c + 1); }, [card]);
useEffect(() => { if (goldCount > 3) setRound((r) => r + 1); }, [goldCount]);
```

Кожна ланка — зайвий рендер, а логіку важко відстежити. Обчисліть увесь наступний стан в одному обробнику події.

### Випадок 5. Ініціалізація з localStorage

```jsx
// ❌ Рендер з порожнім значенням, потім ефект і ще один рендер
const [theme, setTheme] = useState('light');
useEffect(() => { setTheme(localStorage.getItem('theme') ?? 'light'); }, []);

// ✅ Лінива ініціалізація стану: функція виконується лише при першому рендері
const [theme, setTheme] = useState(() => localStorage.getItem('theme') ?? 'light');
```

А от **запис** у `localStorage` при зміні стану — нормальний ефект синхронізації:

```jsx
useEffect(() => {
  localStorage.setItem('theme', theme);
}, [theme]);
```

## 8. Типові помилки. Інші хуки ефектів

### Типові помилки

**Нескінченний цикл.** Ефект змінює стан, від якого залежить:

```jsx
// ❌ count змінюється → ефект → setCount → count змінюється → ...
useEffect(() => {
  setCount(count + 1);
}, [count]);
```

Те саме станеться з ефектом без масиву залежностей, що викликає сеттер, або із залежністю-об'єктом, створеним у рендері.

**Застаріле замикання в інтервалі** (stale closure):

```jsx
// ❌ count у замиканні завжди 0 — лічильник «застряг» на 1
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, []);

// ✅ Функціональне оновлення не залежить від замикання
useEffect(() => {
  const id = setInterval(() => setCount((c) => c + 1), 1000);
  return () => clearInterval(id);
}, []);
```

Функція в `setInterval` створюється один раз, під час першого рендеру, і «бачить» знімок стану з того рендеру (згадайте «стан — це знімок» з практичної 5). Функціональне оновлення розв'язує проблему елегантно.

**Інші помилки:**

| Помилка | Наслідок |
|---|---|
| `useEffect(async () => ...)` | Попередження: ефект має повертати функцію очищення, а не проміс |
| Пропущена залежність | Ефект працює зі застарілими даними |
| Немає очищення підписки | Витоки пам'яті, подвоєння обробників (особливо видно в StrictMode) |
| Ефект замість обробника події | Дія повторюється при повторному монтуванні; складна логіка |
| Виклик хука `useEffect` всередині `if` | Порушення правил хуків — умову пишемо **всередині** ефекту |

### Інші хуки ефектів

| Хук | Коли виконується | Для чого |
|---|---|---|
| `useEffect` | Після малювання екрана | Більшість ефектів |
| `useLayoutEffect` | Після оновлення DOM, **до** малювання | Вимірювання розмірів елемента і зміна позиції до того, як користувач побачить «стрибок» (тултіпи, попапи). Блокує малювання — використовувати рідко |
| `useInsertionEffect` | До змін DOM | Лише для авторів CSS-in-JS бібліотек |

Також у React 19 з'явився хук **`use`**, який може «розгортати» проміс разом із компонентом `<Suspense>`. Він призначений переважно для фреймворків і бібліотек, які кешують проміси; у звичайному клієнтському коді завантаження даних поки що роблять через `useEffect` або бібліотеки.

## Підсумки

- **Побічні ефекти** не можна виконувати під час рендеру. Їх місце — обробники подій або `useEffect`.
- `useEffect` виконується **після** того, як зміни потрапили в DOM і на екран. Його призначення — **синхронізація** компонента із зовнішньою системою.
- **Масив залежностей** містить усі реактивні значення, використані в ефекті: без масиву — після кожного рендеру, `[]` — після монтування, `[a, b]` — при зміні `a` чи `b`. Правило `exhaustive-deps` допомагає не помилитися.
- **Функція очищення** викликається перед повторним запуском ефекту і при розмонтуванні. Вона обов'язкова для таймерів, підписок, слухачів, з'єднань.
- У режимі розробки **StrictMode** виконує «ефект → очищення → ефект», щоб виявити відсутнє очищення.
- Завантаження даних: стани `loading`/`error`/дані, перевірка `res.ok`, захист від стану гонитви через прапорець або **`AbortController`**.
- **Ефект часто не потрібен**: похідні дані обчислюйте під час рендеру, реакцію на дії — в обробниках, скидання стану — через `key`.
