## Як React Native рендерить інтерфейс

### Потоки

У застосунку React Native одночасно працюють кілька потоків:

| Потік | Що робить |
| --- | --- |
| **JS-потік** (JS thread) | Виконує ваш JavaScript: компоненти, хуки, обробники подій, бізнес-логіку, reconciliation React |
| **UI-потік** (main / UI thread) | Нативний потік платформи: малює view, обробляє дотики, нативні анімації та скрол |
| Фонові потоки | Обчислення layout (Yoga), мережа, декодування зображень тощо |

У **New Architecture** (Fabric + TurboModules + JSI), яка увімкнена за замовчуванням в актуальних версіях Expo SDK, JS і нативний код спілкуються напряму через JSI (JavaScript Interface) без старого асинхронного «мосту» (bridge) з JSON-серіалізацією. Це суттєво зменшило накладні витрати, але базове правило залишилося: **якщо JS-потік зайнятий, застосунок не реагує на дії користувача**.

### Бюджет кадру

Плавний інтерфейс — це 60 кадрів на секунду (на сучасних екранах 90–120 Гц ще більше). Отже, на один кадр є:

```
1000 мс / 60 ≈ 16,7 мс
```

За цей час треба виконати JS-код, перерахувати розмітку й передати зміни в UI. Якщо обробник натискання або ре-рендер великого списку займає 50 мс, користувач побачить «підвисання» (dropped frames, jank).

### Чому ре-рендери коштують дорого

Ре-рендер компонента в React — це виклик функції компонента та порівняння нового дерева з попереднім (reconciliation). Сам по собі він дешевий, але:

- при зміні стану батька **за замовчуванням ре-рендеряться всі його нащадки**;
- у списку з сотнею карток кожна зміна стану екрана означає сотню викликів функцій;
- якщо компонент рахує щось важке під час рендеру (фільтрація, сортування), це повторюється щоразу.

:::tip[Головне правило оптимізації]
Спочатку **виміряйте**, потім оптимізуйте. Більшість застосунків працюють нормально без жодної мемоізації. Оптимізуйте конкретне вузьке місце, яке видно в профайлері, а не «про всяк випадок».
:::

## Мемоізація: `React.memo`, `useMemo`, `useCallback`

### `React.memo`

`React.memo` обгортає компонент і пропускає його ре-рендер, якщо пропси **поверхнево рівні** (shallow equal) попереднім.

```jsx
import { memo } from 'react';

function PlaceCard({ place, onPress }) {
  // ...
}

export default memo(PlaceCard);
```

Пастка: поверхневе порівняння бачить нову функцію або новий об'єкт як «інший» проп. Тому такий код зводить `memo` нанівець:

```jsx
// при кожному рендері батька створюються НОВА функція та НОВИЙ об'єкт
<PlaceCard
  place={place}
  onPress={() => navigation.navigate('PlaceDetails', { placeId: place.id })}
  style={{ margin: 8 }}
/>
```

### `useCallback`

`useCallback` повертає ту саму функцію між рендерами, поки не зміняться залежності:

```jsx
const handlePress = useCallback(
  (id) => navigation.navigate('PlaceDetails', { placeId: id }),
  [navigation]
);

// всередині PlaceCard: onPress={() => onPress(place.id)}
<PlaceCard place={place} onPress={handlePress} />
```

### `useMemo`

`useMemo` кешує **результат обчислення**:

```jsx
const favorites = useMemo(
  () => places.filter((p) => p.isFavorite),
  [places]
);
```

Окрім економії обчислень, `useMemo` дає **стабільне посилання** на масив/об'єкт, що важливо, коли результат передається в мемоізований компонент або в залежності `useEffect`.

### Коли мемоізація допомагає, а коли ні

| Ситуація | Чи варто |
| --- | --- |
| Елемент великого списку, що часто ре-рендериться через батька | `memo` + стабільні колбеки — так |
| Важке обчислення (фільтр/сортування сотень елементів) у рендері | `useMemo` — так |
| Функція передається в мемоізований компонент або в залежності ефекту | `useCallback` — так |
| Простий компонент з кількох `Text`, рідко ре-рендериться | Ні — порівняння пропсів коштує не менше за рендер |
| `useCallback` для обробника, переданого в звичайний `<Pressable>` | Ні — користі немає |
| Пропси щоразу різні (наприклад, `children` як JSX) | Ні — `memo` ніколи не спрацює |

:::note[React Compiler]
React Compiler автоматично додає мемоізацію на етапі збірки, і в нових версіях Expo його можна увімкнути в налаштуваннях проєкту. Але розуміння ручної мемоізації залишається необхідним: компілятор не застосовується до коду, що порушує правила хуків, а читати профайлер доведеться все одно.
:::

## Оптимізація списків і зображень

### `FlatList`

`FlatList` — віртуалізований список: він рендерить лише елементи поблизу видимої області, а решту відкидає. Основні пропси для продуктивності:

| Проп | Що робить | Рекомендація |
| --- | --- | --- |
| `keyExtractor` | Стабільний ключ елемента | Завжди `item => item.id`, ніколи індекс |
| `initialNumToRender` | Скільки елементів рендерити при першому показі | Стільки, щоб заповнити екран (≈ 6–10) |
| `maxToRenderPerBatch` | Скільки елементів додавати за одну порцію при скролі | За замовчуванням 10; менше — плавніше, але можливі «білі плями» |
| `windowSize` | Розмір «вікна» рендеру в екранах (за замовчуванням 21 = 10 екранів вгору і вниз) | Зменшення до 5–11 економить пам'ять |
| `removeClippedSubviews` | Відключає невидимі view від нативної ієрархії | Корисно для довгих списків, особливо на Android |
| `getItemLayout` | Повідомляє висоту елемента заздалегідь | Якщо висота фіксована — прибирає вимірювання, пришвидшує `scrollToIndex` |

```jsx
const ITEM_HEIGHT = 120;

<FlatList
  data={places}
  keyExtractor={(item) => item.id}
  renderItem={renderItem}          // винесено в useCallback
  initialNumToRender={8}
  windowSize={7}
  removeClippedSubviews
  getItemLayout={(_, index) => ({
    length: ITEM_HEIGHT,
    offset: ITEM_HEIGHT * index,
    index,
  })}
/>
```

:::caution
Ніколи не рендеріть довгі списки через `ScrollView` + `map()`: так створюються всі елементи одразу, навіть невидимі. `ScrollView` підходить лише для невеликого фіксованого вмісту.
:::

### FlashList

`@shopify/flash-list` — альтернатива `FlatList`, яка **перевикористовує** (recycling) вже створені view замість того, щоб знищувати і створювати їх заново. На довгих списках це помітно плавніше, особливо на слабких Android-пристроях. API майже ідентичний:

```jsx
import { FlashList } from '@shopify/flash-list';

<FlashList
  data={places}
  keyExtractor={(item) => item.id}
  renderItem={({ item }) => <PlaceCard place={item} />}
/>
```

Актуальні версії FlashList розраховані на New Architecture і самі вимірюють розміри елементів (у старіших версіях обов'язковим був `estimatedItemSize`).

### Зображення

Зображення — найчастіша причина повільних списків і великого споживання пам'яті.

- Не завантажуйте фото 4000×3000 для мініатюри 100×100: стискайте при виборі (`quality` в image picker), просіть у сервера потрібний розмір.
- Використовуйте `expo-image` замість стандартного `Image`: дисковий і memory-кеш, плавна поява (`transition`), плейсхолдери (`placeholder`, blurhash), підтримка WebP/AVIF.

```jsx
import { Image } from 'expo-image';

<Image
  source={{ uri: place.image }}
  style={{ width: '100%', height: 180 }}
  contentFit="cover"
  transition={200}
  cachePolicy="memory-disk"
/>
```

- Локальні ресурси (іконки, ілюстрації) додавайте через `require()` — вони потрапляють у збірку і не потребують мережі.

## Анімації, Hermes і розмір бандла

### Анімації на UI-потоці

Якщо анімація рахується в JS-потоці, будь-яке навантаження на JS (завантаження даних, ре-рендер) змусить її смикатися. Тому анімації треба виконувати на UI-потоці.

**Animated API** з `useNativeDriver: true` один раз передає опис анімації в нативну частину, і далі вона відтворюється без участі JS:

```jsx
import { Animated } from 'react-native';

const opacity = useRef(new Animated.Value(0)).current;

useEffect(() => {
  Animated.timing(opacity, {
    toValue: 1,
    duration: 300,
    useNativeDriver: true, // анімація на UI-потоці
  }).start();
}, []);
```

Обмеження: native driver підтримує лише властивості, що не впливають на layout: `opacity` і `transform`. Анімувати `width`, `height`, `top` з ним не можна.

**Reanimated** знімає це обмеження: код анімацій пишеться як *worklets* — маленькі JS-функції, що виконуються прямо на UI-потоці. Можна анімувати будь-які стилі, синхронізувати анімації з жестами (`react-native-gesture-handler`) без затримок.

| | Animated + native driver | Reanimated |
| --- | --- | --- |
| Де виконується | UI-потік (після старту) | UI-потік (worklets) |
| Які властивості | Лише `opacity`, `transform` | Будь-які |
| Зв'язок з жестами | Обмежений | Повний, з gesture-handler |
| Складність | Низька | Середня |

### Hermes

**Hermes** — JS-рушій, оптимізований для React Native, увімкнений за замовчуванням. Під час release-збірки JavaScript компілюється в **байткод** заздалегідь (ahead-of-time). Переваги:

- швидший запуск застосунку (не потрібно парсити й компілювати JS на пристрої);
- менше споживання пам'яті;
- менший розмір завантаження.

### Розмір бандла

- Імпортуйте лише потрібне: `import debounce from 'lodash/debounce'` замість `import _ from 'lodash'`.
- Видаляйте невикористані залежності (`npx depcheck`) та ресурси.
- Не тримайте великі JSON і зображення в бандлі, якщо їх можна завантажити.
- Видаляйте `console.log` з продакшн-збірки (вони сповільнюють JS-потік): плагін `babel-plugin-transform-remove-console`.
- AAB-формат дозволяє Google Play видавати кожному пристрою лише потрібні ресурси й архітектуру.

## Інструменти профілювання

| Інструмент | Як відкрити | Що показує |
| --- | --- | --- |
| **React Native DevTools** | Клавіша `j` у терміналі `npx expo start` | Консоль, точки зупинки (breakpoints), вкладки Components і Profiler |
| **React Profiler** | Вкладка Profiler у DevTools | Які компоненти ре-рендерились, скільки часу тривав кожен коміт, чому відбувся рендер |
| **Perf Monitor** | Меню розробника (струс телефону або `m` у терміналі) → «Toggle Performance Monitor» | FPS JS-потоку та UI-потоку, пам'ять у реальному часі |
| Android Studio Profiler / Xcode Instruments | У development/release збірці | CPU, пам'ять, мережа на нативному рівні |

:::note[Flipper]
Раніше для налагодження RN використовували Flipper. Він більше не підтримується в нових версіях React Native; його замінили React Native DevTools (на базі Chrome DevTools) та інструменти Expo (dev tools plugins).
:::

Типовий порядок роботи з Profiler:

1. Відкрийте DevTools (`j`), вкладка **Profiler**. У налаштуваннях увімкніть «Record why each component rendered».
2. Натисніть «Start profiling», виконайте дію в застосунку (наприклад, додайте в улюблені).
3. Зупиніть запис. На діаграмі **flamegraph** видно всі компоненти, що ре-рендерились, і час кожного.
4. Знайдіть компоненти, які ре-рендерились без потреби (наприклад, усі картки, хоча змінилася одна), застосуйте мемоізацію, повторіть вимірювання і порівняйте.

:::caution[Вимірюйте правильно]
Режим розробки (dev) значно повільніший за release: додаткові перевірки, попередження, відсутність мінімізації. Абсолютні числа в dev-режимі не відображають реальну швидкість — порівнюйте «до» і «після» в однакових умовах, а остаточну перевірку робіть на release-збірці на реальному (бажано недорогому) Android-пристрої.
:::

## Конвеєр випуску застосунку

### Debug і release

| | Debug (development) | Release (production) |
| --- | --- | --- |
| JS | Завантажується з сервера розробки (Metro) | Вбудований у застосунок, скомпільований Hermes у байткод |
| Налагодження | Fast Refresh, DevTools, меню розробника | Вимкнено |
| Оптимізації | Мінімальні | Мінімізація, видалення dev-перевірок |
| Підпис | Debug-ключ | Release-ключ (keystore / сертифікат) |

### Підписування (signing)

Кожен застосунок у магазині має бути **цифрово підписаним**. Підпис гарантує, що оновлення походить від того самого розробника.

- **Android:** використовується файл **keystore** з приватним ключем. Втрата ключа означала неможливість оновити застосунок. Сьогодні Google Play використовує **Play App Signing**: ви підписуєте збірку *ключем завантаження* (upload key), а Google переписує її власним ключем застосунку, тож upload key у разі втрати можна відновити через підтримку.
- **iOS:** потрібні **сертифікат розробника** (distribution certificate) та **профіль забезпечення** (provisioning profile), що пов'язує сертифікат, ідентифікатор застосунку (`bundleIdentifier`) та дозволені можливості.

**EAS керує обліковими даними автоматично:** під час першої збірки EAS пропонує згенерувати keystore (або сертифікати Apple) і безпечно зберігає їх на серверах Expo. Переглянути або завантажити резервну копію можна командою `eas credentials`.

### APK та AAB

| | APK (Android Package) | AAB (Android App Bundle) |
| --- | --- | --- |
| Призначення | Встановлення напряму на пристрій | Завантаження в Google Play |
| Вміст | Усі ресурси для всіх пристроїв | Google Play генерує оптимізовані APK під кожен пристрій |
| Розмір для користувача | Більший | Менший |
| Встановлення вручну | Так | Ні |
| Google Play | Не приймає для нових застосунків | Обов'язковий формат |

Для тестування на своєму телефоні збирають APK, для магазину — AAB.

## EAS: Build, Submit, Update

**EAS (Expo Application Services)** — хмарні сервіси Expo, що закривають увесь цикл випуску:

| Сервіс | Команда | Що робить |
| --- | --- | --- |
| EAS Build | `eas build -p android --profile preview` | Збирає застосунок у хмарі (не потрібні Android Studio чи Mac для iOS) |
| EAS Submit | `eas submit -p android` | Завантажує збірку в Google Play Console / App Store Connect |
| EAS Update | `eas update --channel production` | Доставляє оновлення JS і ресурсів без нової збірки (OTA) |

Профілі збірки описуються в `eas.json`:

```json title="eas.json"
{
  "cli": { "appVersionSource": "remote" },
  "build": {
    "development": { "developmentClient": true, "distribution": "internal" },
    "preview": { "distribution": "internal", "android": { "buildType": "apk" } },
    "production": { "autoIncrement": true }
  },
  "submit": { "production": {} }
}
```

Безкоштовний тариф EAS має обмежену кількість збірок на місяць і чергу очікування, але для навчального проєкту цього достатньо. Збірку можна також виконати локально: `eas build --local` або `npx expo run:android --variant release`.

### Версіонування

Застосунок має **дві** версії:

| Поле | Приклад | Для кого | Правило |
| --- | --- | --- | --- |
| `version` | `"1.2.0"` | Користувач бачить у магазині | Семантичне версіонування: MAJOR.MINOR.PATCH |
| `android.versionCode` | `7` | Google Play | Ціле число, **має зростати** з кожним завантаженням |
| `ios.buildNumber` | `"7"` | App Store | Має зростати в межах однієї `version` |

Google Play відхилить AAB з `versionCode`, який вже був завантажений. Щоб не стежити за цим вручну, в EAS вмикають `"autoIncrement": true` і `"appVersionSource": "remote"` — тоді номер збірки зберігається на серверах EAS і збільшується автоматично.

## Вимоги магазинів, OTA та CI/CD

### Google Play та App Store

| | Google Play | App Store |
| --- | --- | --- |
| Акаунт | Google Play Console, одноразовий реєстраційний внесок | Apple Developer Program, щорічна підписка |
| Тестування | Внутрішнє, закрите, відкрите тестування | TestFlight |
| Обов'язкові матеріали | Опис, іконка 512×512, feature graphic, скриншоти, політика конфіденційності, вікова категорія, форма безпеки даних (Data safety) | Опис, скриншоти для різних екранів, політика конфіденційності, «харчова етикетка» приватності |
| Технічні вимоги | AAB, актуальний `targetSdkVersion` (вимога оновлюється щороку) | Збірка актуальним Xcode/SDK |
| Перевірка | Автоматична + ручна, від годин до кількох днів | Ручне рев'ю, зазвичай 1–2 дні |

:::caution[Нові особисті акаунти Google Play]
Для нових особистих акаунтів розробника Google вимагає перед виходом у продакшн провести **закрите тестування** з певною мінімальною кількістю тестувальників протягом визначеного терміну (на момент написання — 12 тестувальників упродовж 14 днів). Перевіряйте актуальні правила в довідці Play Console.
:::

Типові причини відхилення: збої при запуску, запит дозволів без обґрунтування, відсутня або недоступна політика конфіденційності, невідповідність опису та функціоналу, «порожній» застосунок без цінності, посилання на зовнішню оплату цифрових товарів.

### OTA-оновлення та їхні межі

**OTA (over-the-air)** оновлення через `expo-updates` / EAS Update дозволяють виправити помилку в JS-коді за хвилини, без нової збірки й рев'ю магазину. Застосунок при запуску перевіряє наявність нового бандла на своєму **каналі** (channel) і завантажує його.

| Можна доставити через OTA | Потрібна нова збірка |
| --- | --- |
| Зміни JS-коду: логіка, екрани, стилі | Додавання/оновлення бібліотеки з нативним кодом |
| Зображення та інші ресурси бандла | Зміни в `app.json`, що впливають на нативну частину (дозволи, іконка, splash, `android.package`) |
| Тексти, переклади | Оновлення Expo SDK / React Native |

Сумісність контролює **runtime version**: оновлення доставляється лише збіркам з тим самим `runtimeVersion` (наприклад, політика `appVersion` прив'язує його до `version`). Правила магазинів дозволяють OTA для виправлень і покращень, але не для зміни основного призначення застосунку в обхід рев'ю.

### CI/CD

Збірку й оновлення можна автоматизувати. Найпростіший варіант — **GitHub Actions** з офіційною дією `expo/expo-github-action` і токеном `EXPO_TOKEN` у секретах репозиторію:

```yaml title=".github/workflows/update.yml"
name: EAS Update
on:
  push:
    branches: [main]
jobs:
  update:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - uses: expo/expo-github-action@v8
        with:
          eas-version: latest
          token: ${{ secrets.EXPO_TOKEN }}
      - run: npm ci
      - run: eas update --channel production --message "${{ github.event.head_commit.message }}" --non-interactive
```

Також EAS має власні **EAS Workflows** — конфігурацію в папці `.eas/workflows/`, яка запускає збірки, submit та update за подіями в репозиторії.

## Підсумки

- JS-потік і UI-потік мають вкластися в ≈16,7 мс на кадр; зайнятий JS-потік — це «підвисання» інтерфейсу.
- `React.memo`, `useMemo`, `useCallback` корисні для елементів великих списків і важких обчислень, але без вимірювання часто лише ускладнюють код.
- Списки — через `FlatList` з `keyExtractor`, `initialNumToRender`, `windowSize`, `getItemLayout` або FlashList; зображення — стиснуті та кешовані (`expo-image`).
- Анімації мають працювати на UI-потоці: `useNativeDriver: true` або Reanimated. Hermes компілює JS у байткод і пришвидшує запуск.
- Профілювання: React Native DevTools (`j`), Profiler, Perf Monitor; остаточні виміри — на release-збірці.
- Release-збірка підписується (keystore / сертифікати), EAS керує обліковими даними. APK — для ручного встановлення, AAB — для Google Play.
- EAS Build збирає, EAS Submit завантажує в магазин, EAS Update доставляє OTA-оновлення JS. Нативні зміни потребують нової збірки.
- `version` — для людей, `versionCode`/`buildNumber` — для магазину, і вони мають зростати.

## Контрольні питання

1. Які потоки працюють у застосунку React Native і що станеться з інтерфейсом, якщо JS-потік зайнятий на 200 мс?
2. Чому `React.memo` не спрацює, якщо батьківський компонент передає `onPress={() => ...}`? Як це виправити?
3. Наведіть два випадки, коли `useMemo`/`useCallback` доцільні, і два, коли вони зайві.
4. Які пропси `FlatList` впливають на продуктивність? Коли можна використати `getItemLayout`?
5. Чим FlashList відрізняється від `FlatList`?
6. Чому анімація з `useNativeDriver: true` не смикається під час навантаження JS? Які властивості вона може анімувати?
7. Що таке Hermes і як він впливає на запуск застосунку?
8. Чим APK відрізняється від AAB? Навіщо підписувати застосунок і що таке Play App Signing?
9. Чим відрізняються `version` і `versionCode`? Що робить `autoIncrement` в `eas.json`?
10. Що можна і що не можна оновити через OTA? Яку роль відіграє `runtimeVersion`?
